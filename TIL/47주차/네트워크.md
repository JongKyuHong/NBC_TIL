# 네트워크

## TCP

3 Way HandShake는 회선을 연결하는게 아니라 TCP연결 상태와 초기 시퀀스 번호등을 설정하는 과정
TCP는 패킷단위가 아니고 바이트 스트림을 제공한다

### 흐름 제어

문제 원인 : 수신자의 버퍼 부족
판단 방법 : 수신자가 남은 수신 버퍼 공간을 알려줌
조절 방법 : 수신 윈도우(rwnd)

### 혼잡 제어

문제 원인 : 네트워크 혼잡
판단 방법 : 패킷 손실, RTT변화 등으로 혼잡을 추정
조절 방법 : 혼잡 윈도우(cwnd)등

## Jitter

패킷의 지연시간이 일정하지 않고 변동하는 것

- 라우터에 트래픽이 몰려 패킷이 대기
- 패킷마다 경로 또는 처리 시간이 달라짐
- 송수신 측의 처리 지연이 달라짐

## Interpolation

과거에 수신한 두 위치 사이를 계산해서 중간 위치를 만들어내는 방식
다만 보간할때 두 시점의 데이터를 미리 가지고 있어야 하므로, 일반적으로 일정 시간 과거의 상태를 화면에 표시한다.
단점으로는 화면을 부드럽게 만드는대신 표시지연을 발생시킨다.
만약 100ms의 보간 버퍼를 사용한다면 클라이언트는 서버의 시점보다 약 100ms 이전의 상태를 표시하게 되고, 서버에서 데이터가 도착하기까지의 네트워크 지연도 존재한다.
버퍼를 크게 잡으면 불규칙한 도착에 더 잘대응하지만 화면에 보이는 상태는 더 오래전것이 됨, 반대로 버퍼를 작게 잡으면 패킷이 늦게올때 보간할 데이터가 부족할 수 있다.

## Socket

프로그램이 네트워크 통신을 하기 위해 운영체제에 만들어 놓은 통신용 객체/창구

```
소켓
-> 통신 상태와 정보를 관리하는 OS 객체

포트
-> 그 소켓이 사용할 수 있는 논리적인 번호
```

서버 프로그램이 UDP로 통신하려면

```
프로그램
-> UDP 소켓 생성
-> 로컬 포트 7777에 bind
-> 7777번 포트로 들어오는 UDP 데이터 수신
```

UDP소켓과 TCP소켓

```
UDP 소켓
-> 연결 없이 패킷 단위 통신
-> 하나의 로컬 포트에서 여러 송신자의 데이터를 받을 수 있음

TCP 소켓
-> 연결 기반 통신
-> 서버에서는 보통 연결마다 별도의 connected socket이 생김
-> 접속을 받는 listening socket하나가 있고, 각 연결을 담당하는 여러개의 연결 소켓이 생기는 셈
```

## MTU

한 번의 링크 전송에서 실을 수 있는 IP 패킷 크기의 상한에 가까운 개념
MTU(Maximum Transmission Unit) : 해당 네트워크 구간에서 한 프레임에 실을 수 있는 최대 크기

## IP 단편화

큰 IP패킷 하나를 여러 조각으로 쪼개 보내는 것
IP패킷이 MTU보다 크면 IPv4에서는 조건에 따라 IP계층이 여러 fragment로 쪼갤 수 있다.

```
게임 데이터
↓
UDP가 헤더를 붙임
→ UDP 데이터그램
↓
IP가 헤더를 붙임
→ IP 패킷
↓
Ethernet/Wi-Fi가 헤더를 붙임
→ Frame
↓
실제로 전송
→ 전기/무선 신호, 즉 비트들
```

```
[Ethernet 헤더
    [IP 헤더
        [UDP 헤더
            "Hello"
        ]
    ]
]
```

IP계층에서 MTU보다 크면 조건이 맞다면 IP패킷을 여러개 만들고 이게 각각의 프레임으로 전송된다.

## DNS 캐시

DNS는 도메인 이름 <-> IP주소 바꿔주는 시스템
DNS정보에는 일반적으로 TTL(유효시간)이 설정되어 있고, 캐시가 유효한 동안에는 이전 IP를 사용할 수 있고, 캐시가 만료된 뒤 다시 조회하면 새로운 IP를 얻을 수 있음

## NAT

집안 여러 사설 IP 기기들이 하나의 공인 IP를 공유해서 인터넷을 쓰게 해주는 기능
인터넷에서는 보통 `192.168.x.x`같은 사설 IP로 직접 접근할 수 없다. 대신 공유기가 NAT를 함

```
게임 PC
192.168.0.10:50000
        ↓
공유기 NAT
        ↓
203.0.113.10:62000
        ↓
인터넷 서버
```

서버입장에서는 203.0.113.10:62000 여기서 패킷이 온걸로 보임
서버가 응답하면

```
서버
→ 203.0.113.10:62000
→ 공유기
→ "아, 이건 192.168.0.10:50000 거였지"
→ 게임 PC
```

문제는 외부에서 갑자기 먼저 접속해오는 경우다.
내 PC에서 게임서버를 열었다.

```
게임 서버
192.168.0.10:7777
```

친구가 인터넷에서 203.0.113.10:7777로 접속한다고 했을때 패킷이 공유기까지는 도착하지만

```
203.0.113.10:7777로 패킷이 왔는데...

192.168.0.10으로 보낼까?
192.168.0.11으로 보낼까?
192.168.0.12으로 보낼까?
```

를 알 수 없다. 왜냐하면 내부 PC가 먼저 통신해서 만들어놓은 NAT매핑도 없기 때문

포트포워딩은 이걸 공유기에 미리 알려줌

```
외부에서
203.0.113.10:7777로 들어오면

무조건
192.168.0.10:7777로 보내라
```

이 규칙을 통해

```
친구
→ 203.0.113.10:7777

공유기
→ Port Forwarding 규칙 확인
→ 192.168.0.10:7777

게임 서버
```
