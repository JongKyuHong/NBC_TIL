## 문제 3

다음 코드가 있다고 해보자.

```c++
std::mutex m;

void Update()
{
    m.lock();

    DoSomething();

    m.unlock();
}
```

그런데 DoSomething() 내부에서 예외가 발생했다고 하자.

이 코드에는 어떤 문제가 생길 수 있을까?

그리고 std::lock_guard<std::mutex>를 사용하면 왜 이 문제를 줄일 수 있는지 설명해봐.

---

DoSomething()에서 예외가 발생하면 unlock까지 가지 못하는게 문제임
다른 스레드가 m.lock을 하려고 할때 무한히 대기 할 수 있음 그래서 deadlock같은 상황이 발생할 수 있다.
이를 해결할때는 std::lock_guard<std::mutex> lock(m); 을 사용한다.

```c++
void Update()
{
    std::lock_guard<std::mutex> lock(m);
    DoSomething();
}
```

이렇게 하면 lock_guard가 생성될때 mutex를 잠그고, 함수를 빠져나갈때 알아서 unlock이 된다.

## 문제 4

다음 코드가 있다고 해보자.

```c++
std::condition_variable cv;
std::mutex m;
bool ready = false;
```

한 스레드는 데이터가 준비될 때까지 기다려야 해.

이때 계속:

```c++
while (!ready)
{
// 반복해서 확인
}
```

하는 것과 condition_variable을 사용하는 것은 어떤 차이가 있을까?

특히 CPU 사용량과 스레드 대기 방식 관점에서 설명해봐.

---

ThreadA가 작업중일때 ThreadB는 A가 작업을 끝낸후에 접근할 수 있다. 근데 이때 while문으로 ready되었는지 확인하면 CPU가 계속 반복해서 조건이 맞는지 확인한다 이것을 busy waiting이라고 하는데 TharedB가 실제로 할일은 없는데 CPU코어하나를 계속 쓰는 형태

condition_variable은 깨워줄때까지 재워두는것이라고 보면 된다.

```c++
cv.wait(lock, [&]{
    return ready;
})
```

로 ready가 true일때를 기다림
