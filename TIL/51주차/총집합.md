# push model

일반적인 프로퍼티 복제 : 복제 시스템이 값이 변경되었는지 주기적으로 비교
Push Model : 서버가 값이 변경되었다고 명시적으로 알려 불필요한 비교를 줄임

서버에서 복제 프로퍼티의 값이 변경되었음을 복제 시스템에 직접 알려주는 방식이다.
기존 방식은 복제 시스템이 이전 값과 현재 값을 비교해 변경 여부를 확인한다.
PushModel은 서버 코드가 값이 변경되었을 때 복제 시스템에 알려준다.

적이 1,000마리가 있고, 각 적에게 복제되는 `HP`가 있다고 생각했을때 대부분의 적은 공격받지 않으니까 체력이 그대로 일텐데 기존 방식의 경우는 복제 시스템이 이런 변경되지 않은 값도 확인하는데 비용을 사용할 수 있다. 하지만 Push Model을 사용하면 HP가 변경된 사실을 명시적으로 알려 불필요한 변경 검사 비용을 줄일 수 있다. (Push Model도 Unreal Replication 시스템의 일부)

```c++
void AMyEnemy::GetLifetimeReplicatedProps(
    TArray<FLifetimeProperty>& OutLifetimeProps
) const
{
    Super::GetLifetimeReplicatedProps(OutLifetimeProps);

    FDoRepLifetimeParams Params;
    Params.bIsPushBased = true;

    DOREPLIFETIME_WITH_PARAMS_FAST(
        AMyEnemy,
        HP,
        Params
    );
}
```

이게 핵심이다.

- 서버에서 HP가 변경되면 알림

```c++
void AMyEnemy::TakeDamageFromServer(int32 Damage)
{
    if (!HasAuthority() || Damage <= 0)
        return;

    const int32 NewHP = FMath::Max(0, HP - Damage);

    if (HP == NewHP)
        return;

    HP = NewHP;

    MARK_PROPERTY_DIRTY_FROM_NAME(
        AMyEnemy,
        HP,
        this
    );
}
```

```c++
HP = NewHP;

MARK_PROPERTY_DIRTY_FROM_NAME(AMyEnemy, HP, this);
```

실제 HP를 변경하고 복제 시스템에 HP가 변경되었다고 알림
클라에서는 그냥 OnRep함수 사용하면 된다.

# 선점형/비선점형 스케줄링

1. 선점형 스케줄링

운영체제가 실행 중인 스레드의 CPU 사용을 강제로 중단시키고 다른 스레드에 CPU를 배정할 수 있는 방식

- Game Thread가 CPU를 사용하고 있음
- 더 높은 우선순위의 Worker Thread가 실행 가능해짐
- OS가 Game Thread를 선점하고 Worker Thread에 CPU를 배정함

Windows는 선점형 우선순위 기반 스케줄링을 사용함

2. 비선점형 스케줄링

실행 중인 스레드가 스스로 CPU를 양보하거나, 작업을 마치거나, 대기 상태로 들어가기 전에 운영체제가 강제로 CPU를 빼앗지 않는 방식

- Game Thread가 CPU를 사용하고 있음
- 더 높은 우선순위의 Worker Thread가 실행 가능해짐
- 하지만 Game Thread가 CPU를 양보하지 않으면 Worker Thread는 기다려야 함

따라서 하나의 작업이 너무 오래 실행되면 다른 작업들이 지연될 수 있음

# 벡터 투영

게임에서 플레이어가 레일을 따라 미끄러지는 이동 기능을 구현하고 있다.
현재 플레이어의 속도와 레일의 방향은

```c++
FVector Velocity(300, 400, 0);
FVector RailDirection(1, 0, 0);
```

이렇다. 레일은 X축방향으로만 뻗어있고, 플레이어는 레일을 따라 움직일 수만 있다.

1. 현재 속도 벡터에서 레일 방향으로 움직이는 성분만 추출하려면 어떤 벡터 연산을 활용하면 될까?

벡터 투영을 사용하면 된다.

2. 레일 방향으로 움직이는 속도 벡터를 구하면 결과는?

(300, 0, 0)

여기서 투영이라는 개념이 생기는데
Velocity에서 RailDirection으로 가는 속도가 얼마나 되는지를 확인한다고 보면 된다.
투영의 공식은 V내적D 곱하기 D인데 이는 Velocity와 RailDirection을 내적하면 스칼라 값이 나온다. 여기에 다시 정규화된 RailDirection을 곱하면 해당 벡터방향으로 얼마나 속도를 가지고 있는지 벡터로 나오게 된다.

# MMU(Memory Management Unit)

메모리 관리 장치, CPU안에서 프로그램의 메모리 접근을 처리하는 하드웨어

- 주소변환 : 게임 코드가 사용하는 가상 주소를 실제 물리주소로 바꿈
- 권한 검사 : 그 주소에 대해 지금 시도하는 읽기, 쓰기, 실행이 허용되는지 확인

운영체제가 페이지 테이블에 주소 매핑과 권한을 설정하면, MMU가 메모리에 접근할 때 그 정보를 적용함
TLB는 최근에 확인한 주소 변환과 권한 정보를 보관하는 캐시

# std::lock_guard

공유 뮤텍스의 잠금을 스코프 단위로 관리하는 객체

```c++
void Update()
{
    StateMutex.lock();
    RebuildCache();
    StateMutex.unlock();
}
```

만약 이 상황에서 RebuildCache()에서 예외가 발생하면 unlock이 되지 못하고 빠져나가 버림(호출자가 Update 바깥에서 예외를 잡는다면)

```c++
void Update()
{
    std::lock_guard Guard(StateMutex);
    RebuildCache();
}
```

그때 lock_guard를 쓰면 스코프단위로 관리할 수 있게 함 RAII에도 잘맞음

# explicit

컴파일러가 다른 타입의 값을 그 클래스 객체로 자동 변환하는 것을 막음

```c++
struct Weapon
{
    int Ammo;
    int MaxAmmo;

    explicit Weapon(int Capacity)
        : MaxAmmo(Capacity), Ammo(MaxAmmo)
    {}
};

Weapon Rifle = 30; // 이런거 방지용
```

# Copy-on-Write

여러 프로세스가 같은 데이터를 읽는 동안에는 하나의 물리 메모리 페이지를 공유한다. 한 프로세스가 처음으로 쓰기를 시도하면, 운영체제가
해당 페이지를 복사해 그 프로세스에만 연결한다. 쓰기는 복사본에서 진행된다.

# RAM 파일 캐시

Windows가 하드에서 읽은 파일 내용을 RAM에 보관해 두는 공간, 나중에 같은 파일의 같은 구간을 요청받으면, Windows는 RAM에 남아있는 데이터를 재사용해서 하드 읽기를 줄일 수 있음

1. 첫 실행에서 게임이 맵 파일의 일부를 읽어달라고 요청, 그 데이터가 아직 캐시에 없다면 Windows가 하드에서 읽고, 파일 데이터를 RAM에 보관함, 일반적인 캐시 읽기에서는 요청한 바이트를 게임이 준비한 버퍼로 복사해 줌
2. 게임을 종료하면 게임이 할당한 버퍼와 맵 객체의 수명이 끝남, Windows는 앞서 읽은 파일 데이터를 계속 RAM에 둘 수 있음
3. 두번째 실행에서 새 게임 프로세스가 같은 파일 구간을 요청함. 데이터가 캐시에 남아있다면 Windows는 SSD대신 RAM에서 가져와 새 프로세스에 연결

**실제로 RAM을 차지함**
**당장 다른 용도로 쓸 필요가 없는 RAM에 이미 읽어 둔 데이터를 남겨둠**
