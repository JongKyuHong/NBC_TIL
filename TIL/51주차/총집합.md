# const

const를 섞어서 쓸때 굉장히 헷갈린다.
그나마 쉽게 외울 수 있는 방법을 가져왔다.

- const int\* A : A는 const int를 가리키는 포인터
- int\* const B : B는 int를 가리키는 const포인터
- const int& C : C는 const int에 대한 참조

# push model

일반적인 프로퍼티 복제 : 복제 시스템이 값이 변경되었는지 주기적으로 비교
Push Model : 서버가 값이 변경되었다고 명시적으로 알려 불필요한 비교를 줄임

서버에서 복제 프로퍼티의 값이 변경되었음을 복제 시스템에 직접 알려주는 방식이다.
기존 방식은 복제 시스템이 이전 값과 현재 값을 비교해 변경 여부를 확인한다.
PushModel은 서버 코드가 값이 변경되었을 때 복제 시스템에 알려준다.

적이 1,000마리가 있고, 각 적에게 복제되는 `HP`가 있다고 생각했을때 대부분의 적은 공격받지 않으니까 체력이 그대로 일텐데 기존 방식의 경우는 복제 시스템이 이런 변경되지 않은 값도 확인하는데 비용을 사용할 수 있다. 하지만 Push Model을 사용하면 HP가 변경된 사실을 명시적으로 알려 불필요한 변경 검사 비용을 줄일 수 있다. (Push Model도 Unreal Replication 시스템의 일부)

```c++
void AMyEnemy::GetLifetimeReplicatedProps(
    TArray<FLifetimeProperty>& OutLifetimeProps
) const
{
    Super::GetLifetimeReplicatedProps(OutLifetimeProps);

    FDoRepLifetimeParams Params;
    Params.bIsPushBased = true;

    DOREPLIFETIME_WITH_PARAMS_FAST(
        AMyEnemy,
        HP,
        Params
    );
}
```

이게 핵심이다.

- 서버에서 HP가 변경되면 알림

```c++
void AMyEnemy::TakeDamageFromServer(int32 Damage)
{
    if (!HasAuthority() || Damage <= 0)
        return;

    const int32 NewHP = FMath::Max(0, HP - Damage);

    if (HP == NewHP)
        return;

    HP = NewHP;

    MARK_PROPERTY_DIRTY_FROM_NAME(
        AMyEnemy,
        HP,
        this
    );
}
```

```c++
HP = NewHP;

MARK_PROPERTY_DIRTY_FROM_NAME(AMyEnemy, HP, this);
```

실제 HP를 변경하고 복제 시스템에 HP가 변경되었다고 알림
클라에서는 그냥 OnRep함수 사용하면 된다.

# 스레드 상태

- Running : CPU에서 명령어 실행 중
- Ready : 실행할 준비가 되었지만 CPU 배정을 기다림
- Waiting : I/O 완료 등 특정 이벤트를 기다려 현재 실행할 수 없음

# 선점형/비선점형 스케줄링

1. 선점형 스케줄링

운영체제가 실행 중인 스레드의 CPU 사용을 강제로 중단시키고 다른 스레드에 CPU를 배정할 수 있는 방식

- Game Thread가 CPU를 사용하고 있음
- 더 높은 우선순위의 Worker Thread가 실행 가능해짐
- OS가 Game Thread를 선점하고 Worker Thread에 CPU를 배정함

Windows는 선점형 우선순위 기반 스케줄링을 사용함

2. 비선점형 스케줄링

실행 중인 스레드가 스스로 CPU를 양보하거나, 작업을 마치거나, 대기 상태로 들어가기 전에 운영체제가 강제로 CPU를 빼앗지 않는 방식

- Game Thread가 CPU를 사용하고 있음
- 더 높은 우선순위의 Worker Thread가 실행 가능해짐
- 하지만 Game Thread가 CPU를 양보하지 않으면 Worker Thread는 기다려야 함

따라서 하나의 작업이 너무 오래 실행되면 다른 작업들이 지연될 수 있음
