# CPU가 쓰기 권환을 확인하는 구체적인 방법

페이지 테이블에는 가상 주소와 물리 주소의 대응 관계뿐 아니라 읽기/쓰기 등 메모리 접근 권한 정보도 있다.
CPU의 메모리 관리 장치인 MMU가 주소를 변환하면서 이 권한을 검사함, 이때 TLB에 캐시된 주소 변환 정보도 활용할 수 있다.

## Dirty Page와 차이점

Dirty Page는 쓰기 권한 검사와 다른 개념이다.

- 접근 권한 검사 : 이 메모리에 쓰기를 해도 되는가?
- Dirty Page : 메모리 페이지가 쓰기 작업으로 변경되었는가?

## 흐름

1. CPU가 메모리 쓰기 명령 실행
   Data[0] = 100

2. MMU가 접근 권한 확인
   페이지 테이블/TLB의 권한 정보 활용, MMU란 CPU의 메모리 관리 장치

3. 쓰기 권한 없음
   실제 메모리 쓰기 차단, CPU예외 발생

4. Windows가 예외 처리
   권한 위반으로 판단하면 접근 위반 예외 전달

---

허용 상태라면

3. 쓰기 가능 확인
4. 가상 주소 -> 물리 주소 변환
5. CPU캐시를 통해 값 100 기록
6. 해당 메모리 내용 변경 완료

# 윈도우 파일 공유 모드

```
1. 내가 이 파일로 뭘 할 건가?
   → 읽기 / 쓰기
   → GENERIC_READ, GENERIC_WRITE

2. 내가 열어둔 동안 다른 프로그램에게 뭘 허용할 건가?
   → 다른 프로그램의 읽기 / 쓰기 / 삭제 허용
   → FILE_SHARE_READ, FILE_SHARE_WRITE, FILE_SHARE_DELETE
```

예를들어

```c++
CreateFileW(
    L"GameData.bin",
    GENERIC_READ,      // 나는 읽겠다
    FILE_SHARE_READ,   // 다른 프로그램도 읽는 건 허용
    ...
);
```

이렇게 파일을 열었다면

> 나는 읽기 위해 파일을 열었고, 내가 파일을 열고 있는 동안 다른 프로글매도 읽기 용도로 여는 것은 허용하겠다.

라는 뜻이다.

```c++
GENERIC_READ,
0,
```

이렇게 열었다면 다른 프로그램이 이 파일을 공유해서 사용하는것은 허용하지 않겠다는 뜻

## 이런 기능을 제공하는 이유

- 여러 프로그램이 게임 데이터를 동시에 읽어야 할 때는 읽기 공유를 허용
- 게임 런처가 실행 중인 게임 파일을 업데이트하려고 할 때는 충돌하는 파일 접근을 제한할 수 있다.
- 중요한 파일을 쓰는 동안 호환되지 않는 다른 프로그램의 열기 요청을 막을 수 있다.

# 핸들 상속

```
Windows에서 게임 런처가 Game.exe를 실행한다고 하자.

런처는 게임 시작에 필요한 설정 데이터를 전달하기 위해 운영체제의 Pipe(파이프) 기능을 사용하려고 한다.

Pipe는 한 프로그램에서 보낸 데이터를 다른 프로그램이 읽을 수 있도록 하는 통신 수단이야.

현재 상황은 다음과 같아.

1. 런처가 Pipe를 생성하고, 데이터를 읽는 데 사용할 핸들을 확보했다.
2. 해당 핸들은 자식 프로세스에 전달할 수 있도록 생성했다고 가정한다.
3. 런처는 CreateProcessW()로 Game.exe를 실행하며, bInheritHandles 인자를 FALSE로 설정했다.
4. 런처는 Pipe 핸들의 숫자 값을 실행 인자로 Game.exe에 전달했다.
5. Game.exe는 전달받은 숫자를 핸들로 사용해 Pipe에서 데이터를 읽으려 했지만 실패했다.

질문
1. 런처가 올바른 핸들 값을 전달했는데도 Game.exe에서 사용할 수 없는 이유는 무엇일까?
2. 런처가 생성한 Pipe를 Game.exe에서도 사용할 수 있게 하려면 운영체제의 프로세스 생성 과정에서 무엇을 준비해야 할까?
3. 반대로 런처가 가진 모든 자원에 게임 프로세스가 접근할 수 있도록 허용한다면 어떤 문제가 발생할 수 있을까?
   이번 문제는 서로 다른 프로세스가 운영체제 자원을 전달받아 사용하는 과정을 중심으로 설명
```

프로세스 간 핸들 상속, IPC + 프로세스별 Handle Table 문제

Windows에서 Handle은 운영체제 자원의 주소가 아니라

```
프로세스의 Handle Table
100 -> Pipe 객체
104 -> File 객체
108 -> Event 객체
```

처럼 그 프로세스가 어떤 커널 객체를 사용할 수 있는지 나타내는 참조값
그래서 런처가 Handle = 100을 갖고 있다고 해서 Game.exe에 숫자 100만 전달하면 되는게 아님
Game.exe 쪽에서도 그 Pipe에 대한 유효한 Handle이 있어야함

bInheritHandles = FALSE; 라서 자식 프로세스가 부모의 상속 가능한 핸들을 전달받지 않는다.

```
Launcher
Handle 100 → Pipe
라고 해도 Game쪽에서는
Game.exe
Handle 100 -> 없음 / 다른 의미
```

모든 핸들을 막 상속시키면 안되는 이유는 파일, Pipe, Event같은 필요없는 커널 자원까지 자식 프로세스가 접근할 수 있게 되어 보안/자원 관리 문제가 생길 수 있음

# DLL

Dynamic Link Library (동적 연결 라이브러리)

## DLL이란?

프로그램에서 사용할 함수나 기능을 별도의 파일로 제공하는 라이브러리

.lib는 정적 라이브러리 파일로서 라이브러리 코드를 실행파일등에 포함하고, 실행시 해당 정적 라이브러리 파일은 보통 불필요하다.

.dll은 동적 라이브러리 파일로서 별도 DLL을 실행 시 로드하여 사용하는 방식이고 필요한 DLL을 찾을 수 있어야 한다.

## Windows 로더의 역할

Game.exe를 실행하면 Windows는 실행 파일을 준비하면서 필요한 DLL도 확인하고 로드함

```
Game.exe 실행 요청
-> Windows 로더 (Import Table등을 통해 필요한 DLL 확인)
-> DLL 검색 및 로드(DLL의 필요한 함수 참조 연결)
-> 런타임 초기화 -> Main()실행

```

여기서 중요한건 일반적인 DLL 의존성은 main()이 시작하기 전에 로드될 수 있다.
따라서 필수 DLL이 없으면 main()까지 도달하지 못할 수 있다.

# 스케줄링과 CPU자원 배분

## 스케줄러가 필요한 이유

- 요리사 4명 = CPU 논리 코어 4개
- 요리 주문 10개 = 실행할 준비가 된 스레드 10개
- 주방 매니저 = 운영체제 스케줄러

스케줄러는 실행 가능한 스레드 중 어떤 스레드를 어느 논리 CPU에서 실행할지 결정하는 역할을 한다
CPU는 프로세스 자체가 아니라 프로세스 안의 스레드를 실행한다

## CPU는 어떤 스레드를 먼저 실행할까?

- Ready : 실행할 준비가 되었지만 CPU를 배정받지 못함
- Running : 실제 CPU에서 명령어를 실행 중
- Waiting : I/O나 동기화등의 조건을 기다려 실행할 수 없는 상태

Windows 스케줄러는 일반적으로 우선순위가 높은 실행 가능 스레드를 먼저 선택하고, 같은 우선순위의 스레드들에는 CPU시간을 나누어 배정함. 더 높은 우선순위의 스레드가 준비되면 실행 중인 낮은 우선순위 스레드를 선점할 수도 있음

**선점**

1. CPU 0에서 우선순위가 낮은 작업 A가 실행중
2. 우선순위가 높은 작업 B가 실행 가능해짐
3. 운영체제가 A의 실행을 중단시키고 B를 실행할 수 있다
4. A는 나중에 다시 CPU를 배정받아 이어서 실행함

선점은 CPU를 다른 스레드에 넘기기로 하는것이고, Context Switching은 그 과정에서 실행 상태를 저장/복원하는 작업

### 게임에서는 왜 중요할까?

어떤 PC에 논리 CPU가 8개가 있다.
Unreal 게임을 실행했는데 다음과 같은 현상이 발생했음

- CPU전체 사용률은 25%정도
- GPU사용률도 높지 않음
- 그런데 게임은 40FPS정도밖에 나오지 않음
- Game Thread에서 오래 걸리는 작업이 발견

CPU사용률이 25%라면 CPU성능이 충분히 남아있는것 아닐까?
-> 꼭 그렇지만은 않다.

예를들어 논리 CPU8개중 하나만 계속 바쁘고 나머지는 한가한 상황이라고 생각하면 Game Thread가 주로 한 논리 CPU에서 실행되는 동안 계속 바쁘다면, 다른 CPU가 놀고 있어도 그 스레드의 작업을 자동으로 나누어 실행하지는 못함

그래서 두 개념을 구별해서 봐야함

- CPU 전체 사용률 : 시스템 전체 논리 CPU들이 얼마나 바쁜가?
- 특정 스레드 병목 : 게임 진행에 중요한 스레드가 프레임을 제시간에 끝내지 못하는가?

즉, CPU사용률이 낮더라도 특정 스레드가 병목일 수 있다.

## CPU Affinity

CPU Affinity는 특정 스레드가 실행될 수 있는 CPU의 범위를 제한하는 설정

특정 요리사 1번이 하나의 요리를 전담으로 하는느낌
장점은 같은 요리사가 계속 맡으면 작업 연속성과 캐시 지역성에 유리할 가능성이 많다
단점은 요리사 1번이 바쁘고 나머지가 한가해도 해당 요리는 다른 요리사에게 맡길 수 없다.

Affinity는 CPU를 전용으로 확보하는게 아니라 특정 스레드가 실행될 수 있는 CPU를 제한하는 기능이다. 그래서 다른 스레드 즉 요리사 1번은 다른요리도 하면서 Affinity설정된 요리는 전담으로 하는것

### Unreal에서는 어떻게?

게임 FPS가 떨어졌다면

1. Unreal Insights로 Game, Worker, Render Thread의 실행 시간을 확인한다.
2. 오래 걸리는 함수나 작업이 있는지 확인한다
3. 계산량이 많은 것인지, 다른 스레드나 I/O를 기다리는 것인지 구분한다
4. 실제 원인에 따라 작업량 감소, 병렬화, 잠금 경합 개선등을 적용한다.
5. Affinity나 우선순위 조정은 필요성이 측정으로 확인되었을때 검토한다.

# 멀티 스레딩

예를들어 몬스터 1,000마리의 이동 경로를 계산한다고 했을때
단일 스레드는 1~1000마리의 경로 계산을 한스레드가 순차처리한다.
멀티 스레딩은 CPU0은 Worker ThreadA에서 몬스터 1~500마리 CPU1은 Worker Thread B에서 501~1000마리를 병렬로 처리한다. 즉, 두 스레드가 서로 다른 논리 CPU에서 동시에 계산이 가능하다.
물론 작업을 나눌 수 있어야 하고, 스레드 간 의존성이나 동기화 비용도 고려해야함

## Unreal의 게임스레드는?

Game Thread는 한 순간에 하나의 논리 CPU에서만 실행됨 하지만 Game Thread가 다른 스레드에 계산 작업을 맡기는 것은 가능

1. Game Thread가 몬스터 1,000마리의 경로 계산을 요청
2. Worker Thread A와 B가 경로를 나눠서 병렬 계산
3. 계산 결과를 안전하게 Game Thread에 전달
4. Game Thread가 그 결과를 이용해 몬스터의 이동 상태를 갱신

하지만 Unreal에서는 Actor의 상태 변경 등 Game Thread에서 처리해야 하는 작업이 많기 때문에 모든 코드를 무작정 Worker Thread로 옮길 수는 없다.
