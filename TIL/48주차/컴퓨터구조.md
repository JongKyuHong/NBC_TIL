# Conflict Miss

CPU캐시에 빈 공간이 남아 있어도, 서로 다른 데이터가 캐시의 같은 위치(Set)에 배치되어야 해서 기존 데이터가 밀려나는 현상

## 왜 발생할까?

CPU캐시는 데이터를 아무 위치에나 저장하는게 아니라, 메모리 주소에 따라 저장할 수 있는 캐시Set이 정해져 있음

```
CPU Cache (단순화)

Set 0 → [ A ]
Set 1 → [   ]
Set 2 → [   ]
Set 3 → [   ]

A 접근 → Set 0에 A 저장
B 접근 → Set 0에 B 저장 (A 제거)
A 접근 → Set 0에 A 저장 (B 제거)
B 접근 → Set 0에 B 저장 (A 제거)
```

캐시의 다른 Set은 비어 있어도 계속 Cache Miss가 발생

## 구조

실제 CPU캐시는 보통 Set-Associative Cache구조를 사용한다.

2-Way Set-Associative Cache, 각 Set에 캐시 라인 2개까지 저장할 수 있다고 가정하면
Set0에 A,B가 들어있을때 C도 Set 0에 배치되어야 한다면 자리가 없으므로 A나 B를 제거해야 한다.

---

실제 개발시에는 프로파일링을 통해 발견하게 되면 데이터 배치 변경, 배열 사이 패딩 추가, 접근 패턴 변경등으로 수정해야 한다.

# 비트연산자

- & : AND역할
- | : OR
- ^ : XOR
- ~ : NOT
- << : 왼쪽 시프트
- `>>` : 오른쪽 시프트

시프트 연산

```c++
unsigned int A = 1u;  // 0001

A << 1; // 0010 (2)
A << 2; // 0100 (4)
A << 3; // 1000 (8)

unsigned int B = 8u; // 1000

B >> 1; // 0100 (4)
B >> 2; // 0010 (2)
```

---

만약에 상태이상을 int의 비트로 사용한다면

```c++
constexpr unsigned int Poison     = 1u << 0; // 0001
constexpr unsigned int Stun       = 1u << 1; // 0010
constexpr unsigned int Stealth    = 1u << 2; // 0100
constexpr unsigned int Invincible = 1u << 3; // 1000

unsigned int State = 0;
```

각비트에 다른 상태를 넣음, 상태 켜기

- 상태 켜기

```c++
State |= Poison;
```

만약에 현재 상태가 0100(은신)이라면 OR연산으로 Poison상태 켜주기

- 상태 끄기 : AND + NOT(& ~)

```c++
State &= ~Poison;
```

~Poison은 0001에서 반대인 1110을 AND로 하면, 포이즌이 켜져있건 안켜져있건 무조건 꺼짐

- 상태 확인 : AND(&)

```c++
if ((State & Poison) != 0)
{
  // 중독 상태
}
```

- 상태 반전 : XOR(^)

```c++
State ^= Poison;
```

실제 알고리즘 비트마스킹에서는 더 어려운개념이 많지만 상태이상할때는 이정도면 될듯

# 메모리 정렬(Memory Alignment), 비정렬 메모리 접근(Unaligned Memory Access)

## 메모리 정렬

메모리정렬이란 CPU가 데이터를 효율적으로 읽고 쓰도록 자료형이 요구하는 주소 경계에 데이터를 배치하는 것
일반적인 환경에서

- char : 1바이트, 1의 배수 주소
- short : 2바이트, 2의 배수 주소
- int : 4바이트, 4의 배수 주소
- double : 8바이트, 8의 배수 주소

## 비 정렬 접근

4바이트 단위 경계를 기준으로 보면

```
정렬된 경우

[1000 1001 1002 1003] [1004 1005 1006 1007]
                         └──── int ────────┘

비정렬된 경우

[1000 1001 1002 1003] [1004 1005 1006 1007]
                  └──────── int ─────┘
```

비정렬된 경우에는 데이터가 경계를 걸치게 됨
CPU 구조에 따라 이런 접근을 처리하기 위한 추가 작업이 발생할 수 있음
특히 서로 다른 캐시 라인 두개에 걸치면 두 캐시 라인에 접근해야 하므로 성능이 떨어질 수 있다.

# 컴파일러 최적화와 하드웨어 메모리 접근

```
문제 4 / 5 — 외부 장치의 값이 바뀌지 않는 문제
게임 컨트롤러의 상태를 확인하는 저수준 코드를 작성한다고 하자.
int* Status = GetDeviceStatusAddress();

while (*Status == 0)
{
    // 장치 준비 대기
}

StartInputProcessing();


Status는 일반 메모리가 아니라, 하드웨어 장치의 상태를 읽을 수 있는 특별한 메모리 주소를 가리킨다고 가정하자.

장치가 준비되면 하드웨어가 해당 값을 1로 바꾼다.

그런데 최적화된 빌드에서는 장치가 준비됐는데도 반복문을 빠져나오지 못하는 문제가 발생했다.

질문
1. 컴파일러는 어떤 판단을 해서 이런 문제를 일으킬 수 있을까?
2. CPU가 매번 실제 장치의 상태를 확인하도록 하려면 코드에서 무엇을 고려해야 할까?
정확한 C++ 문법을 몰라도 괜찮아. 원리를 중심으로 설명해 봐.
```

컴파일러는 일반 변수의 값이 반복문 안에서 바뀌지 않는다고 판단하면, 매번 메모리를 읽는 대신 처음 읽은 값을 재사용하도록 최적화할 수 있음
실제로는 CPU가 아니라 하드웨어 장치가 값을 변경하는 상황, 컴파일러가 이런 외부 변경을 고려하지 않고 값을 재사용하면 장치의 상태가 바뀌어도 반복문을 빠져나오지 못할 수 있다.

## 해결법

메모리 매핑 I/O에서는 `volatile`이 사용될 수 있다.
`volatile`은 컴파일러에 해당 메모리 접근을 임의로 생략하거나 하나의 읽기로 합치지 말라고 알려주는 역할을 함
컴파일러가 코드를 최적화할 때, 프로그램 외부에서 발생하는 값의 변경을 일반 변수 읽기만으로는 인식하지 못할 수 있다는 점을 기억하자

# SIMD

문제 2 / 5 — 동일한 계산을 반복하는 코드의 처리 속도 차이
게임에서 대량의 float 데이터를 갱신하는 함수가 있어.
void Apply(float* Dst, const float* Src, int Count)
{
for (int i = 0; i < Count; ++i)
{
Dst[i] = Src[i] \* 2.0f;
}
}

이 함수를 두 가지 방식으로 호출한다고 하자.

상황 A — 서로 다른 배열
float Src[10000];
float Dst[10000];

Apply(Dst, Src, 10000);

상황 B — 같은 배열에서 겹치는 구간
float Data[10001];

Apply(Data + 1, Data, 10000);

두 상황 모두 같은 함수를 호출하고, 반복 횟수도 같아.

그런데 컴파일러가 최적화한 결과 A가 B보다 훨씬 빠르게 실행될 수 있다고 하자.

질문

1. A에서는 컴파일러가 여러 원소의 계산을 한꺼번에 처리하는 방식으로 최적화할 수 있어. 어떤 원리일까?
2. B에서는 왜 컴파일러가 동일한 최적화를 적용하기 어려울 수 있을까?
   정확한 용어를 몰라도 코드의 읽기·쓰기 관계를 보고 추론해 봐.

---

1. A가 빠를 수 있는 이유 SIMD
   일반적으로 CPU는 숫자를 하나씩 계산할 수 있지만, SIMD를 활용하면 하나의 명령어로 여러 숫자를 동시에 계산할 수 있다.

2. B에서는 왜 어려울까?

```c++
Data[1] = Data[0] * 2;
Data[2] = Data[1] * 2;
Data[3] = Data[2] * 2;
```

이런식으로 동작함, 두번째 줄이 첫번째 줄에서 변경한 값을 읽는다는 점, 따라서 계산을 한번에 실행하면 원래 코드와 결과가 달라질 수 있다.
SIMD로 여러 원소를 동시에 계산하려면 반복 간 데이터 의존성이 없는지 확인해야 함

# 서멀 스로틀링

문제 3 / 5 — 게임을 오래 실행할수록 느려지는 PC
어떤 노트북에서 게임을 실행했어.

- 게임을 시작한 직후에는 120FPS를 유지함.
- 약 30분이 지나자 75FPS 정도로 떨어짐.
- 게임의 오브젝트 수, 메모리 사용량, 그래픽 설정은 거의 변하지 않음.
- CPU 온도는 처음 60°C였지만 시간이 지나면서 95°C까지 상승함.
- CPU 사용률은 비슷한데 동작 클럭은 처음 4.2GHz에서 2.4GHz로 떨어짐.
  질문

1. CPU 사용률은 비슷한데 FPS가 떨어진 이유는 무엇일까?
2. CPU가 스스로 동작 클럭을 낮추는 이유는 무엇일까?
3. 이 문제가 게임 코드의 계산량 증가 때문인지, 하드웨어의 동작 상태 때문인지 어떻게 구분할 수 있을까?
   알고 있는 범위에서 답해 봐.

---

게임 개발에서 프레임 저하의 원인을 분석할때 알면 좋은 개념

1. CPU사용률은 비슷한데 왜 FPS가 떨어질까?
   CPU 사용률과 CPU의 처리 속도는 다른 개념이다.
   예를들어 CPU가 계속 바쁘게 일하고 있더라도 동작 클럭이 낮아지면 같은 시간 동안 처리할 수 있는 작업량이 줄어들 수 있음

2. CPU가 왜 스스로 클럭을 낮출까?
   과열을 막기 위해서, CPU는 온도가 지나치게 올라가거나 전력/전류 제한에 도달하면 동작 속도를 낮출 수 있음
   이것을 **쓰로틀링**이라고 하고, 특히 발열로 인해 속도를 제한하는 현상을 서멀 스로틀링이라고 함

3. 코드 문제인지 하드웨어 문제인지 어떻게 구분할까?
   프로파일링과 하드웨어 상태를 함께 확인

- 게임 코드 측정 : 프레임당 CPU작업 시간과 함수별 실행 비용 확인
- 하드웨어 상태 측정 : CPU온도, 실제 동작 클럭, 스로틀링 여부 확인
- 비교 실험 : PC가 식은 상태와 뜨거운 상태에서 동일한 게임 장면 실행
