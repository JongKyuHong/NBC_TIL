# 아웃런 조작법 가이드 설계

## 배경

현재 `UNSOutRunGuideSubsystem`은 아웃런(허브)에서 "캐릭터 선택 콘솔 → 게임시작 콘솔 → 신규 NPC" 순으로 목적지 안내(마커+HUD 텍스트)만 제공한다. 이동/점프/대시 같은 기본 조작법 안내가 없어서, 처음 접속한 유저가 조작을 모를 수 있다

## 목표

아웃런 진입 시 목적지 안내 앞 단계로 조작법 안내(이동 → 점프 → 대시)를 추가한다. 인런에는 적용하지 않는다.

## 요구사항

1. 조작법 안내 순서: 이동(WASD) → 점프(Space) → 대시(Shift) → 기존 캐릭터 콘솔 안내 → 게임시작 콘솔 안내 → 신규 NPC 안내
2. 각 조작법 단계는 **해당 행동 1회 발동** 또는 **타임아웃 경과** 중 먼저 오는 조건으로 완료 처리한다.
   - 이동: 이동 입력이 한 번이라도 들어오면 완료 (W/A/S/D 개별 체크 아님)
   - 점프: 점프 액션 1회 발동
   - 대시: 대시 어빌리티(`Ability_Common_Dash`) 입력 1회 발동
3. 상호작용 키 안내는 별도 단계를 만들지 않는다 (기존 캐릭터 콘솔 상호작용이 곧 상호작용 튜토리얼 역할).
4. 타임아웃은 `DT_GuideText`의 `AutoAdvanceSeconds` 필드로 행마다 설정한다. `0`이면 타임아웃 없음(무한 대기) — 기존 콘솔/NPC 안내 행은 값 미설정으로 지금과 동일하게 동작.
5. 타임아웃으로 자동 진행된 단계도 실제 행동으로 완료된 것과 동일하게 취급하여 영구 저장한다 (다음에 또 뜨지 않음).
6. 조작법 안내는 계정당 1회 — `NSPermanentSaveGame`에 플래그를 저장한다.
7. 아이콘은 지금 추가하지 않는다. 추후 `FNSGuideTextData`에 필드 추가로 확장 가능한 구조를 유지한다 (지금은 텍스트만)

## 데이터 변경

### `NSPermanentSaveGame.h`

기존 `bCharacterConsoleGuideDone` 위쪽에 3개 플래그 추가:

```cpp
bool bMoveGuideDone = false;
bool bJumpGuideDone = false;
bool bDashGuideDone = false;
```

### `FNSGuideTextData` (`NSGuideTextData.h`)

필드 추가:

```cpp
// 0이면 타임아웃 없음 — 실제 행동/상호작용 전까지 무한 대기
UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "UI")
float AutoAdvanceSeconds = 0.0f;
```

### `DT_GuideText` (에디터 작업, 사용자가 직접)

행 3개 추가: `MoveInput`, `JumpInput`, `DashInput`. `AutoAdvanceSeconds`에 10 정도 입력 (밸런스는 에디터에서 조정). 기존 행(`CharacterSelectConsole`, `NSReadyStartActor`, `NewNPC`)은 그대로 둔다.

## 코드 변경

### `NSOutRunGuideSubsystem.h/.cpp`

- `NotifyMoveInput()` / `NotifyJumpInput()` / `NotifyDashInput()` 추가 — 기존 `NotifyCharacterConsoleUsed()`와 동일한 패턴:
  - `bGuideStarted` 게이트 체크
  - **현재 안내 우선순위가 자기 단계일 때만** 완료 처리 (순서 보장 — 예: 이동 안내가 떠 있지 않은데 우연히 이동 입력이 들어와도 무시하지 않고, 애초에 이동 안내 중에만 호출되도록 판정)
  - 완료 → 플래그 세팅 → `SaveGuideState()` → `RefreshGuide()`
- `RefreshGuide()`/`UpdateGuideText()`의 우선순위 체인 맨 앞에 이동/점프/대시 3단계 추가 (기존 `bNeedCharacterGuide` 등과 동일한 방식의 `bNeedMoveGuide`/`bNeedJumpGuide`/`bNeedDashGuide`)
- 타임아웃 처리: 안내 텍스트를 세팅하는 시점에 해당 행의 `AutoAdvanceSeconds > 0`이면 `FTimerHandle`로 타이머 시작. 만료 시 해당 단계 완료 경로(Notify와 동일)를 그대로 호출. 안내가 다른 단계로 바뀌거나 입력으로 먼저 완료되면 타이머를 취소한다.
- 조작법 3단계는 목적지가 없으므로 마커 토글 없음 — HUD 텍스트만 갱신.

### `NSInputBinderComponent.cpp`

- `Input_Move(const FInputActionValue& Value)`: 이동값이 0이 아닐 때 `GetWorld()->GetSubsystem<UNSOutRunGuideSubsystem>()->NotifyMoveInput()` 호출 (조용히 무시 패턴, 기존 콘솔 Notify 호출부와 동일)
- `Input_Jump()`: 함수 진입 시 `NotifyJumpInput()` 호출
- `Input_AbilityPressed(FGameplayTag InputTag)`: `InputTag == NSGameplayTags::Ability_Common_Dash`일 때 `NotifyDashInput()` 호출

## 영향 범위 확인

- 인런에서는 `bGuideStarted`가 `false`이므로(아웃런 진입 시에만 `StartGuide()` 호출) 모든 Notify가 조용히 무시됨 — 기존 게이트 재사용, 별도 분기 불필요.
- 이미 조작법 안내를 완료한 계정은 플래그가 모두 `true`이므로 아웃런 재진입 시 바로 기존 콘솔 안내부터 시작 (기존 동작과 동일).

## 확인된 전제

- 아웃런(허브)에서 점프/대시 어빌리티가 실제로 활성화되어 있음 (사용자 확인 완료).

## 1. NPC 상호작용 UI를 닫으면 게임 인풋이 안 먹는 버그

### 증상

파츠 NPC(장착/업그레이드)는 정상인데, 펫 강화 NPC와 공용 업그레이드 NPC는 UI를 닫은 후 이동 등 게임 인풋이 전혀 먹지 않음.

### 원인

- NPC 상호작용 시작 시 `ANSPlayerController::OpenInteractionWidget`이 위젯을 열면서 `InputBinder`의 활성 입력 태그를 UI 전용으로 바꿔 게임플레이 IMC를 제거함.
- 이 게임플레이 IMC 복원은 오직 `NotifyInteractionWidgetClosed()`(컨트롤러 측)에서만 일어나는데, 각 상호작용 위젯이 `CloseWidget()` 안에서 이 통지를 직접 호출해줘야 하는 구조였음.
- 파츠 장착/업그레이드 위젯 2개는 통지를 호출했지만, 펫 강화·공용 업그레이드 위젯은 빠뜨림 → `SetInputMode(GameOnly)`는 걸리는데 캐릭터의 게임플레이 IMC 자체는 복원되지 않아 키 입력이 무시됨.

### 근본 원인 진단

`UNSNPCInteractionWidgetBase`가 빈 가상 함수 2개(`OpenForInteractor`/`CloseWidget`)만 있는 순수 껍데기였고, `OwningController` 멤버와 "닫을 때 통지" 절차를 파생 위젯 4개(`NSPartUpgradeWidget`, `NSPartEquipWidget`, `NSPetUpgradeWidget`, `NSCommonUpgradeWidget`)가 각자 복붙해서 구현하던 구조. 복붙 과정에서 통지 호출이 2곳에서 누락됨.

### 해결

`UNSNPCInteractionWidgetBase`를 템플릿 메서드 패턴으로 재구성:

- `OwningController`를 베이스로 이동 (파생 클래스 중복 선언 제거)
- `CloseWidget()`을 **non-virtual 최종 진입점**으로 만들어 `OnCloseWidget()`(파생 클래스 커스텀 정리) → 컨트롤러 통지(`NotifyInteractionWidgetClosed`) → `RemoveFromParent()` 순서를 항상 보장
- 파생 위젯은 `CloseWidget()` 대신 `OnCloseWidget()`만 override — 통지를 빠뜨릴 수 없는 구조로 변경

## 2. Common 등급에 유효 스탯이 없는 파츠(대시 파츠 등)가 드랍/상점에 노출

### 증상

대시 횟수 증가 파츠처럼 Common 등급 `ValueRangesByRarity` 키가 정의되지 않은 파츠가 필드 드랍, 인런 상점 재고, 아웃런 파츠 카탈로그에 스탯 없는 상태로 등장.

### 원인

드랍/상점 생성 로직이 **파츠를 먼저 뽑고 나서** 스탯을 등급으로 필터링하는 순서였음. "등급 키 없음 = 그 등급에서 제외"라는 규칙이 스탯 선택 단계에만 적용되고, 파츠 선택 단계에는 적용되지 않아 유효 스탯이 하나도 없는 파츠도 그대로 선택될 수 있었음.

### 해결

파츠 선택 이전에 "이 등급에서 유효한 스탯이 1개 이상인 파츠"만 후보로 거르도록 3곳 모두 순서를 바꿈:

1. **필드 드랍** (`NSRewardHandler::MakePartDataFromDropResult`): 등급 해석 → 후보 필터링 → 파츠 선택 순서로 변경
2. **인런 상점 재고** (`NSPartEquipComponent::GenerateShopStock`): "파츠 선택 → 등급 롤"에서 "등급 롤 → 그 등급 유효 파츠만 후보 수집 → 선택"으로 순서 변경
3. **아웃런 카탈로그** (`NSPartEquipWidget::BuildPartEntries`): Common에서 유효 스탯 없는 파츠는 카탈로그 자체에서 제외
4. **아웃런 구매 방어선** (`NSProgressionSubsystem`의 구매 함수): UI 필터를 우회해 호출되더라도 유효 스탯 없으면 구매 자체를 차단 (2차 방어)

## 3. 설계 변경: 아웃런 파츠 구매 수치를 랜덤 대신 고정값으로

### 배경

아웃런 파츠 구매는 재도전이 없는 1회성 구매라 랜덤 롤이 "운"의 영역이 되는 게 부적절하다고 판단, 해당 등급(Common) 범위의 **최대값으로 고정**하도록 설계 변경.

### 해결

- `NSProgressionSubsystem`의 구매 함수에서 `FMath::RandRange(Range.Min, Range.Max)` → `Range.Max` 고정값으로 변경
- `NSPartDetailWidget::SetupFromDefinition`(아웃런 카탈로그 미리보기)도 "효과 : {스탯} {최소}~{최대}" 범위 표시에서 "효과 : {스탯} {최대값}" 고정값 표시로 변경 (구매 로직과 일치)

## 4. 파츠 스탯 수치 표시 개선 — 단위(%·초) + 증가/감소 라벨

### 요구사항

- 확률형 스탯(크리티컬 확률 등)은 수치 뒤에 `%` 표시
- 시간형 스탯(쿨다운 감소 등)은 수치 뒤에 `초` 표시
- 실제 수치 뒤에 부호에 따라 "증가"/"감소" 라벨 부착 (예: 쿨다운 감소 파츠가 -2를 가지면 "2초 감소"로 표시 — 절댓값 + 단어로 표현해 마이너스 기호와 라벨이 겹치지 않게 함)
- 범위 미리보기(리롤 변동폭, 다음 등급 범위)처럼 방향이 아직 확정되지 않은 곳은 단위만 적용하고 증가/감소는 생략

### 해결

- `FNSStatDisplayInfoRow`에 `ENSStatDisplayUnit`(없음/%/초) 필드 `DisplayUnit` 추가 — 에디터에서 스탯별로 지정
- 공용 포맷 함수 `NSPartUtils::FormatStatValueText(WorldContext, StatTag, Value, bShowDirection=true)` 신설 — 기존에 3곳(NSPartDetailWidget, NSPartUpgradeWidget, NSPartSlotButton)에 흩어져 있던 "소수점 내림 포맷" 로컬 헬퍼를 이 함수 하나로 통합
- 아웃런 카탈로그/장착 상세, 인런 파츠 슬롯 버튼, 인런 업글/리롤 패널 전부 이 함수를 사용하도록 교체

### 에디터 작업 필요

스탯 표시 DT(`DT_PartStatDisplay`)에서 확률형/시간형 스탯에 `DisplayUnit` 값을 지정해야 실제로 반영됨. 지정 안 하면 기존처럼 단위 없이 수치+증가/감소만 표시.

## 6. 인런 상점 구매가격 표시를 BuyPriceText 대신 CostText로 통합

### 배경

인런 상점 재고 클릭 시 가격이 `NSPartUpgradeWidget` 자체의 `BuyPriceText`에 표시되고 있었는데, 바로 위 `WBP_PartDetail`(`StockDetailWidget`)에 이미 `CostText`가 있어서 중복 위젯이었음.

### 해결

- `UNSPartDetailWidget::SetupFromInstance`에 `int64 Price = -1` 파라미터 추가. `Price >= 0`이면 `CostText`에 "비용 : {Price}" 표시, 기본값(-1)이면 비용 줄 생략(장착중인 파츠 표시 등 판매 대상이 아닌 경우)
- `NSPartUpgradeWidget::OnStockEntryClicked`에서 `EquipComp->GetShopPrice(...)`로 가격을 계산해 `StockDetailWidget->SetupFromInstance(Item, Def, Price)`로 전달
- `BuyPriceText` 필드 및 관련 코드 제거

### 에디터 작업 필요

WBP에서 이제 안 쓰는 `BuyPriceText` 바인딩 위젯은 삭제해도 무방. `StockDetailWidget`(WBP_PartDetail)의 `CostText`가 화면에 노출되도록 배치 확인.

## 7. 아웃런 조작법 가이드 — 대시 안내가 안 사라지는 버그

### 증상

이동/점프 안내는 정상적으로 다음 단계로 넘어가는데, 대시(Shift) 안내만 아무리 눌러도 사라지지 않음.

### 원인

`NSInputBinderComponent::Input_AbilityPressed`에서 대시 입력을 감지하려고 `InputTag == NSGameplayTags::Ability_Common_Dash`로 비교했는데, 이건 **어빌리티 자신을 식별하는 태그**(`GA_Dash`의 `AssetTags`, `TryActivateAbilitiesByTag` 같은 데서 씀)였음. 실제로 `Input_AbilityPressed`에 넘어오는 `InputTag`는 GAS 입력 바인딩용 태그(`UNSAbilitySystemComponent::AbilityInputTagPressed`가 `AbilitySpec.GetDynamicSpecSourceTags()`와 매칭)라서, 서로 다른 태그 계층인 두 값이 절대 일치하지 않아 알림이 아예 호출되지 않았음.

### 해결

비교 대상을 입력 전용 태그로 교체: `InputTag == NSGameplayTags::Input_Ability_Dash` (`NSGameplayTags_Input.h`에 선언된 `"Input.Ability.Dash"`).

### 교훈

GAS에서 "어빌리티 자체 태그"(`AssetTags`, `TryActivateAbilitiesByTag`용)와 "입력 바인딩 태그"(`InputTag`, `AbilityInputTagPressed`용)는 이름이 비슷해 보여도 완전히 다른 값일 수 있다. 어빌리티 활성화 방식(태그 기반 vs 입력태그 기반)에 따라 어느 쪽 태그를 비교해야 하는지 먼저 확인할 것.

- `Source/NeoSanctum/Character/Component/NSInputBinderComponent.cpp` (`Input_AbilityPressed`)
- `Source/NeoSanctum/Tag/NSGameplayTags_Input.h`, `NSGameplayTags_Ability.h`

## 8. 아웃런 조작법 가이드 — 완료 조건 설계를 두 번 뒤집음

### 배경

아웃런 진입 시 이동→점프→대시 순으로 조작법을 안내하는 기능을 추가하면서, "언제 다음 단계로 넘어가는가" 기준이 논의 중 두 번 바뀜.

1차: 입력 1회 발동 **또는** DT의 `AutoAdvanceSeconds` 경과(둘 중 먼저 오는 쪽) → 입력이 들어오면 즉시 완료.
2차: 텍스트가 뜨자마자 실제 이동 여부와 상관없이 몇 초 뒤 사라지는 게 이상하다는 피드백으로, "키 입력은 전부 받되, 입력이 들어온 시점부터 `AutoAdvanceSeconds`만큼 대기 후 완료"로 변경(최종). 즉 입력이 없으면 영원히 안 넘어가고, 입력 후에도 즉시 사라지지 않고 지정된 초만큼 텍스트가 더 보임

### 최종 구조

- `NotifyMoveInput/NotifyJumpInput/NotifyDashInput`: 입력이 들어오면 (그리고 이전 단계가 끝났으면) `StartStageTimeout()` 호출
- `StartStageTimeout(RowName, CompleteFunc)`: 이미 타이머가 도는 중이면 무시(반복 입력에 재시작 안 됨). `DT_GuideText`에서 `AutoAdvanceSeconds`를 찾아 그 시간 뒤 완료 함수 호출. 값이 0 이하면 즉시 완료
- `UpdateGuideText()`는 텍스트 표시만 담당, 타이머는 전혀 건드리지 않음(표시만으로는 절대 자동 진행 안 됨)

### 교훈

"타임아웃 자동 진행" 기능을 넣을 때는 "입력 없이도 자동으로 넘어가야 하는가"와 "입력 후 텍스트를 얼마나 더 보여줄 것인가"를 처음부터 구분해서 확인받을 것. 이번엔 이 둘을 섞어서 설계했다가 두 번 되돌렸음

## 9. 캐릭터 선택 콘솔 — 같은 BP를 두 곳에 배치했는데 마커가 둘 다 뜸

### 증상

캐릭터 선택 콘솔(`ANSCharacterSelectNPC`)이 레벨에 두 인스턴스 배치되어 있음(게임 시작 옆 / `CommonUpgradeNPC` 구출 후 갈 수 있는 NPC방). 튜토리얼 단계에서 게임 시작 옆 콘솔에만 마커가 떠야 하는데 둘 다 뜸.

### 잘못된 접근 (1차)

`ANSInteractableNPCBase`의 `NPCId` 필드가 이미 있길래 여기에 구분값을 넣고 `UnlockedNPCIds`로 해금 여부를 체크하는 코드를 넣었음. 하지만 캐릭터 선택 콘솔은 애초에 `NPCId`를 쓰는 액터가 아니었고(항상 비어있음), 사용자가 원한 것도 "해금 여부에 따라 마커 표시"가 아니라 "같은 BP 중 특정 배치 인스턴스 하나만 항상 마커 대상"이었음. 완전히 다른 요구사항에 엉뚱한 필드를 재활용한 것.

### 해결

같은 블루프린트의 특정 배치 인스턴스만 구분하는 표준 방법인 **액터 태그(Actor Tags)** 사용. 게임 시작 옆 인스턴스에만 에디터에서 `GuideTutorial` 태그를 붙이고, 코드는 `ActorHasTag(TEXT("GuideTutorial"))`로 체크.

```cpp
// 캐릭터 선택 콘솔 마커 —> 같은 BP가 여러 곳에 배치되므로, 레벨에서 "GuideTutorial" 태그를 붙인 인스턴스(게임 시작 옆)만 튜토리얼 대상
for (TActorIterator<ANSCharacterSelectNPC> It(GetWorld()); It; ++It)
{
	const bool bIsTutorialConsole = It->ActorHasTag(TEXT("GuideTutorial"));
	SetActorMarkerLocal(*It, bNeedCharacterGuide && bIsTutorialConsole);
}
```

### 교훈

"같은 클래스의 여러 배치 인스턴스 중 하나만 구분"하고 싶을 때는 그 클래스에 이미 있는 필드를 억지로 재해석하지 말고 액터 태그부터 검토할 것. 필드를 재활용하면 그 필드의 원래 의미(여기선 "해금 조건")가 오염돼서 나중에 헷갈림.

### 관련 파일

- `Source/NeoSanctum/Core/Waypoint/NSOutRunGuideSubsystem.cpp` (`RefreshGuide`)

### 에디터 작업 필요

게임 시작 옆 `ANSCharacterSelectNPC` 인스턴스의 Details → Actor → Tags에 `GuideTutorial` 추가. NPC방 쪽 인스턴스는 태그 없이 그대로 둠

## 10. 가이드 텍스트 위젯 — Border 안 TextBlock이 과도하게 줄바꿈됨

### 증상

`Border > TextBlock` 구조로 가이드 텍스트 배경을 만들었는데, 배경 폭을 다 채우기 전에 몇 글자마다 줄바꿈이 일어남.

### 원인

TextBlock의 Border 슬롯 Horizontal Alignment가 `Center`였음. Auto Wrap은 "할당된 폭" 기준으로 줄바꿈하는데, HAlign=Center인 위젯은 부모의 전체 폭이 아니라 자기 컨텐츠의 최소 폭만 할당받아서, 그 좁은 폭 기준으로 계속 줄바꿈이 발생함.

### 해결

- TextBlock의 Border 슬롯 **Horizontal Alignment → Fill** (전체 폭을 할당받게 함 → 줄바꿈이 배경 폭 기준으로 일어남)
- 텍스트 자체는 **Justification → Center**로 가운데 정렬 (HAlign=Fill과 별개 속성 — Fill은 "얼마나 넓게 차지할지", Justification은 "그 폭 안에서 글자를 어디에 놓을지")
- `Auto Wrap Text` 체크 필요

이 두 속성을 같이 설정하면 짧은 텍스트("대시")는 완전 정중앙에, 긴 문장은 배경 폭을 다 채우고 줄바꿈되면서 각 줄이 가운데 정렬됨.

### 참고

Border가 내용물 크기에 따라 늘어나는 구조(부모가 HorizontalBox/VerticalBox + Size To Content)라면 Auto Wrap의 기준 폭이 안 잡힐 수 있음 — 그럴 땐 `Wrap Text At`에 픽셀값을 직접 지정하거나 Border를 Size Box로 감싸 폭을 고정.

### 에디터 작업 필요

가이드 텍스트 WBP에서 TextBlock 선택 → Slot(Border Slot)의 Horizontal Alignment를 Fill로, Details의 Justification을 Center로 변경.
