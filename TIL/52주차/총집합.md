# check, verify, ensure 차이

## check

코드가 반드시 지켜야 하는 전제를 확인할때 씀
`check(Inventory != nulltr);`이거는 이 지점까지 왔다면 인벤토리가 준비돼 있어야 한다는 뜻
개발중에 전제가 깨지면 그 자리에서 멈추므로 원인을 찾기가 쉬움

`Inventory != nullptr`은 값을 확인하기만 하므로, Shipping에서 이 검사가 빠져도 인벤토리를 만드는 작업에는 영향이 없다.

## verify

괄호 안의 작업 자체가 출시 빌드에서도 실행돼야 할 때 씀
`verify(LoadSettingsFromDisk());` 는 개발 빌드와 Shipping 모두에서 파일을 읽음. 개발 중 읽기에 실패하면 그 자리에서 멈춤, 기본 Shipping에서는 읽기에 실패해도 다음 줄로 진행

출시버전에서 파일이 없을때 기본 설정을 적용해야 한다면, 반환 값을 if로 검사해서 기본 설정을 적용하는 코드를 별도로 작성해야 한다.

## ensure

문제가 생겼다는 기록을 남기면서 복구할 수 있을때 씀

```c++
if (ensure(HealthBar != nullptr))
{
    HealthBar->SetPercent(HealthRatio);
}
```

HealthBar가 nullptr이면 ensure가 false를 반환해서 if 본문을 건너뜀, 갱신을 건너뛰게 하는 건 바깥의 if
ensure만 한줄 쓰고 다음 줄에서 HealthBar를 사용하면 그 줄까지 그대로 실행 됨

# 메모리 순서와 release/acquire

`std::atomic`을 사용하면 해당 변수의 읽기·쓰기를 원자적으로 처리할 수 있다. 다른 변수까지 안전하게 전달하려면 스레드 사이의 메모리 순서도 보장해야 한다.

## memory_order_relaxed

해당 atomic 변수의 연산을 원자적으로 처리한다. 다른 데이터의 쓰기와 읽기 사이에는 동기화 관계를 만들지 않는다.

따라서 일반 변수에 데이터를 쓰고, relaxed로 준비 완료를 알리는 것만으로는 다른 스레드가 그 데이터를 안전하게 읽는다고 보장할 수 없다.

## release와 acquire

데이터를 준비한 쪽은 `release`로 준비 완료 신호를 저장한다. 사용하는 쪽이 `acquire`로 그 신호를 읽으면, 신호 이전에 기록한 데이터를 안전하게 읽을 수 있다.

```cpp
// 두 스레드를 시작하기 전에 초기화
int Data = 0;
std::atomic<bool> Ready{false};

// 로딩 스레드
Data = 42;
Ready.store(true, std::memory_order_release);

// 사용하는 스레드
if (Ready.load(std::memory_order_acquire))
{
    Use(Data);
}
```

이 예제는 준비 완료 이후 `Data`를 다시 수정하지 않는 조건이다.

`release`로 저장한 `true`를 `acquire`로 읽으면, `Data`에 쓰는 작업이 `Data`를 읽는 작업보다 먼저 일어났다는 **happens-before 관계**가 성립한다.

# DLL과 Windows 로더

## DLL

**Dynamic-Link Library**, 동적 연결 라이브러리다. 컴파일한 함수와 데이터를 별도 `.dll` 파일에 담아 프로그램에서 불러와 사용할 수 있다.

예를 들어 오디오 기능을 `Audio.dll`로 분리하면, 게임이 사용하는 함수와 바이너리 호환성을 유지하면서 해당 DLL을 따로 업데이트할 수 있다.

## Windows 로더

프로그램이 DLL 안의 함수를 실행할 수 있도록 준비하는 운영체제 구성 요소다.

- 필요한 DLL 파일을 찾는다.
- DLL의 코드와 데이터를 프로세스의 가상 주소 공간에 매핑한다.
- 필요한 다른 DLL을 불러오고 주소 정보를 처리한다.
- 프로그램이 호출할 함수의 실제 주소를 연결한다.
- DLL 초기화를 수행한다.

실행 파일을 시작할 때 연결하는 방식에서는 가져올 함수의 주소를 **Import Address Table(IAT)**에 연결한다.

실행 중 코드에서 직접 불러올 때는 `LoadLibrary()`로 DLL을 로드하고, `GetProcAddress()`로 외부에 공개된 함수의 주소를 얻어 호출할 수 있다.

# Object Pool / Arena / Slab 차이

- Object Pool
  특정 객체를 재사용, 객체 생성/파괴 비용을 줄이는게 목적

- Arena Allocator
  큰 메모리 덩어리 하나를 잡아두고 앞에서부터 빠르게 할당, 개별 해제를 거의 안하고 전체 Reset한다
  예시) 한 프레임 동안만 사용하는 임시 데이터

- Slab Allocator
  같은 크기의 메모리 블록을 대량으로 관리한다. Object Pool과 비슷하지만 Object Pool은 게임 객체 재사용 관점
  Slab은 메모리 할당 시스템 관점

# 타입 추론

```c++
void Inspect(Weapon& W);
void Inspect(Weapon&& W);

template<typename T>
void Relay(T&& Value)
{
    Inspect(Value);
}

Weapon Sword;
Relay(Sword);     // 기존 객체 전달
Relay(Weapon{});  // 임시 객체 전달
```

여기서 원하는 동작은 기존 객체는 `Weapon&`로, 임시 객체는 `Weapon&&`로 전달하는것이다.
실제 동작은 둘다 Inspect(Weapon&)으로 전달된다.
Inspect(Value)를 어떻게 바꾸면 될까?

---

우선 Sword의 경우 T가 Weapon&으로 추론된다(Lvalue이므로). 그리고 &&를 만나서 Weapon& &&이므로 축약되어 Weapon&로 Value의 타입이 정해진다.

Weapon{}의 임시 객체의 경우 T가 Weapon으로 추론된다.(prvalue), 그리고 &&를 만나서 Weapon&&로 Value의 타입이 정해지는데 Inspect(Value)로 넘어갈때는 Value라는게 Lvalue이므로 둘다 Weapon&이 호출된것
이를 방지하기 위해서는

`Inspect(std::forward<T>(Value))`로 변경해주면 된다. 이는 Value의 원래 타입 정보를 이용해 다음 함수에 전달할 표현식의 성격을 결정한다.

# SMT와 SIMD

- SMT : 한 물리 코어가 여러 하드웨어 스레드의 명령을 처리한다. 실행 유닛등을 공유하며, 한 스레드가 기다리는 동안 다른 스레드의 명령을 실행해 자원 활용도를 높일 수 있다.
- SIMD : 여러 데이터에 같은 연산을 한 명령으로 적용한다.

# 하드웨어 스레드

하드웨어 스레드는 프로세스 하나를 전담하는게 아니라 운영체제가 배정한 소프트웨어 스레드를 실행하는 자리이다. 게임 프로세스 안에서도 게임 스레드, 렌더 스레드등이 있는데 운영체제는 이 스레드들을 하드웨어 스레드에 배정한다. 실행하던것을 잠시 멈추고 다른 프로그램의 스레드를 실행시키기도 하므로, 특정 프로세스에 고정된 자리는 아니다.

# 프로세스, 스레드, CPU코어의 관계

- 프로세스 : 실행중인 프로그램, 게임 프로세스 하나 안에 여러 스레드가 존재할 수 있다(게임 스레드, 렌더 스레드, 작업스레드 여러개)
- 소프트웨어 스레드 : 프로그램 안에서 명령을 실행하는 흐름
  - 게임 스레드 : 게임 로직을 담당, 일반적인 언리얼 게임에서는 하나
  - 렌더 스레드 : 렌더링 명령을 준비한다.
  - 작업 스레드 : 경로 탐색, 데이터 가공 등의 작업을 나눠 처리하며 여러 개 존재할 수 있다.
- 물리 코어 : 명령을 실제로 처리하는 하드웨어 실행 장치를 가진다.
- 하드웨어 스레드 : 운영체제가 소프트웨어 스레드를 배정할 수 있는 CPU의 실행 자리, 논리 프로세서라고도 한다.

# 스레드가 CPU에서 실행되는 방식

운영체제가 실행 가능한 소프트웨어 스레드를 하드웨어 스레드에 배정
게임 프로세스의 여러 스레드가 여러 물리코어에서 동시에 실행될 수 있다. 특정 코어가 특정 프로세스를 전담하는 것은 아니며, 같은 스레드도 실행 도중 다른 코어로 옮겨질 수 있다.
기존 코어의 캐시를 활용하기 위해 같은 코어에서 계속 실행하려는 경향이 있지만(Affinity, 친화성), 고정 배치를 보장하지는 않는다.
게임이 실행 중이어도 모든 순간 CPU를 사용하는 것은 아니다. GPU작업이나 입출력 등의 완료를 기다리는 동안에는 다른 프로그램의 스레드가 CPU를 활용할 수 있다.

# SMT

SMT는 하나의 물리 코어가 여러 하드웨어 스레드를 제공하는 기술이다.
각 하드웨어 스레드는 별도의 실행 상태를 유지하지만, 물리 코어의 실행 유닛등은 공유한다. 한 스레드가 메모리 접근 등을 기다리는 동안 다른 스레드의 명령을 처리해 자원 활용도를 높일 수 있다.
따라서 4코어 8스레드 CPU는 물리코어 8개와 같은 성능을 보장하지 않는다.

# 작업 스레드와 스레드 풀

작업 스레드는 여러 개 만들 수 있다. 보통은 여러 작업 스레드를 미리 만들어 두고 대기 중인 작업을 나눠 맡기는 스레드 풀을 사용한다.
소프트웨어 스레드 수가 하드웨어 스레드 수보다 많으면 운영체제가 번갈아 실행시킨다. 따라서 스레드를 많이 만든다고 무조건 빨라지는 것은 아니다.
