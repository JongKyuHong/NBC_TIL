# 읽기/쓰기 잠금(Reader-Writer Lock)

읽는 사람 끼리는 데이터를 바꾸지 않으니까 함께 들어가도됨, 반면 수정하는 사람은 읽는 사람까지 모두 나간 뒤 혼자 들어가야 함

`std::shared_mutex`로 접근 방식에 따라 다른 잠금을 잡는다.

```c++
std::shared_mutex TableMutex;

void ReadItem()
{
    std::shared_lock Lock(TableMutex); // 공유잠금
}

void UpdateItem()
{
    std::unique_lock Lock(TableMutex); // 배타 잠금
}
```

수정할때는 배타 잠금을 사용해 다른 조회와 수정을 모두 막는다.
C++에서는 같은 std::shared_mutex에 조회는 std::shared_lock, 수정은 std::unique_lock을 사용한다.

# UDP와 IP 단편화

- MTU는 해당 경로에서 단편화 없이 운반할 수 있는 IP 패킷 크기의 상한이다.
- IP 단편화로 나뉜 조각은 수신 측에서 재조립한 뒤 UDP로 전달한다.
- 조각이 유실되어 재조립하지 못하면 해당 UDP 데이터그램 전체가 전달되지 않는다
- 게임 데이터의 크기는 MTU에서 IP/UDP 헤더 크기를 뺀 값 이하로 제한해야 단편화를 피할 수 있다.

```
보낼 때
게임 데이터 → UDP 헤더 추가 → IP 헤더 추가 → 네트워크 전송

받을 때
네트워크 수신 → IP 처리·필요하면 재조립 → UDP 처리 → 게임
```

- IP단편화 : IP 패킷 하나가 전송 가능한 크기보다 커서, 여러 작은 IP패킷으로 쪼개지는 것

# Overlap과 Hit

- Overlap
  두 컴포넌트의 충돌 영역이 겹칠때 발생함. Sphere뿐 아니라 Box, Capsule 등에서도 발생할 수 있음

- Hit
  충돌 응답이 Block인 상태에서 이동 중 충돌하거나 물리 시뮬레이션으로 부딪히는 등의 상황에서 발생함.

만약에 검이 적을 통과하며 데미지를 주는 방식이라면 Overlap을 사용해야 한다. Hit는 주로 이동이 차단되는 충돌에 사용함
단, 빠르게 움직이는 검은 프레임 사이에 적을 통과할 수 있어서 별도의 Sweep Trace등을 활용하기도 함

# Control Block

shared_ptr과 weak_ptr의 Control Block은 소유권 관리를 위한 별도의 관리 정보이다.

- Strong Count : 객체를 소유한 shared_ptr의 수
- Weak Count : 객체를 관찰하는 weak_ptr의 수
- 객체를 해제하는 데 필요한 관리 정보(삭제자 등)

약참조든 강참조든 남아있다면 Control Block은 살아있고 남은 소유 자체가 없어지면 해제될 수 있다.
(shared_ptr 참조 카운트가 0이면 관리 대상 객체가 소멸하지만, weak_ptr이 남아있다면 Control Block은 계속 존재할 수 있다.)

# CPU캐시의 충돌 미스와 매핑 방식

CPU는 RAM의 데이터를 일반적으로 캐시라인 단위로 가져옴
그런데 캐시가 비어있는데도 충돌이 나는 경우가 있음
메모리 주소에 따라 데이터를 저장할 캐시 위치가 제한될 수 있다는것

## 캐시 배치 방식

캐시를 배치하는 방식에는 크게 세가지가 있는데

- Direct-Mapped : 정해진 한 위치에 저장, 단순하고 빠르지만 충돌에 취약하다.
- Set-Associative : 정해진 집합(Set) 내 여러 위치, 충돌 가능성을 줄일 수 있다.
- Fully Associative : 캐시 내 임의의 위치에 저장, 배치가 자유롭지만 하드웨어 비용이 증가

## Direct-Mapped

메모리블록 A,B가 캐시 슬롯0에만 들어간다면 A->B->A->B이렇게 접근할때 충돌이 날 수 있다.

이때 재미있는건 같은 슬롯에 있는 A와B를 캐시는 어떻게 구별하냐는것이다.
이는 메모리 주소를 나누는 방식에 Tag, Index, Offset이 있는데
Tag는 어떤 블록인지? Index는 어떤 슬롯인지? Offset은 라인은 어느 위치인지? 정보를 가지고 있음
이들은 캐시 하드웨어가 물리주소의 정해진 비트를 Tag, Index, Offset으로 사용한다.
CPU가 주소 A에 접근한다 했을때

1. Index를 이용해 해당 캐시 위치를 확인
2. 저장된 Tag가 A와 같은 Tag인지 확인
3. 같고 유효하다면 캐시 히트, 다르면 캐시 미스인거임
4. 히트 했다면 Offset으로 캐시 라인 내부의 필요한 데이터를 선택함

## 충돌 미스를 줄이는 방법

- 방법 A Set-Associative Cache

한 집합 안에 여러 캐시라인을 저장하도록 하는 방식
2-Way Set-Associative라면, 같은 Set에 매핑된 A와 B를 두 Way에 각각저장
여기서 Set은 슬롯(Way)하나가 아니라 여러개가 모인 한 묶음(행)
2Way이므로 2개의 슬롯이 하나의 Set이된다.

- 방법 B 데이터 배치 변경

프로그래머 입장에서는 메모리 배치를 변경해 충돌을 줄일 수 있다.
예를 들어 특정 간격으로 떨어진 배열들이 계속 같은 캐시 Set에 매핑된다면, 데이터의 배치나 간격을 조정해서 충돌을 완화할 수 있음
다만 이는 캐시 구조와 실제 접근 패턴에 따라 효과가 달라지므로 측정이 필요하다.

## 캐시 미스의 종류

- Compulsory Miss : 처음 접근하는 데이터라 캐시에 아직 없음
- Capacity Miss : 캐시 용량이 부족해 필요한 데이터를 유지하지 못함
- Conflict Miss : 캐시에 빈공간이 있어도 매핑 위치가 충돌함

# 텍스처 이미지를 GPU에서 사용할 수 있게 하려면

디스크에 있는 텍스처 이미지를 GPU에서 어떻게 활용할 수 있을까?
우선 이미지파일을 GPU가 사용할 수 있는 텍스처 리소스로 만드는 과정이 필요하다.

1. 디스크에서 PNG파일을 읽음
2. PNG를 디코딩해서 픽셀 데이터를 얻음
3. DirectX 11에서 `ID3D11Texture2D` 리소스를 생성하고 픽셀 데이터를 업로드
4. 해당 텍스처를 셰이더에서 읽을 수 있도록 SRV(Shader Resource View)를 생성함
5. Pixel Shader에서 UV좌표를 이용해 텍스처를 샘플링함

## SRV

셰이더가 GPU리소스를 읽을 수 있도록 제공하는 뷰

```c++
ID3D11Texture2D* Texture;

```

Texture : 실제 텍스처 데이터를 저장하는 GPU리소스
TextureSRV : 셰이더가 해당 리소스를 읽을 때 사용하는 뷰

# 셰이더

셰이더는 GPU에서 실행되는 프로그램으로, 정점의 위치를 변환하거나 화면에 표시할 색상을 계산하는 역할을 한다.
게임에서 3D 모델을 화면에 그릴 때 대표적으로 두 종류의 셰이더가 사용된다.

1. Vertex Shader(정점 셰이더)
   3D모델의 정점 데이터를 처리하는 프로그램
   캐릭터의 정점 위치를 World -> View -> Projection 변환에서 화면에 투영할 수 있는 좌표로 만듦

2. Pixel Shader(픽셀 셰이더)
   래스터화된 Fragment의 색상 등을 계산하는 프로그램
   Fragment : 3D 삼각형을 화면에 투영하고 래스터화할 때 생성되는 픽셀 후보 데이터

SIMD 레지스터는 여러 숫자를 동시에 담고 연산할 수 있는 레지스터이다.

# deque의 내부 구조

여러 개의 연속된 메모리 블록을 관리하면서, 앞과 뒤에 원소를 효율적으로 추가하거나 제거할 수 있도록 만든 자료구조

deque구현에는 크게 두가지가 있다.

1. 데이터 블록(Block) : 실제 원소들이 저장되는 연속된 메모리 공간
2. 블록 포인터 배열(Map) : 각 데이터 블록의 주소를 관리하는 배열
   Map은 std::map이 아님, 내부 데이터 블록을 찾기 위한 포인터 배열을 말함

Block A 내부의 원소들은 메모리 연속적으로 있음
Block B 내부의 원소들도 메모리 연속적으로 있음
하지만 Block A, B가 실제로 메모리에서 서로 붙어있다는 보장이 없음
즉, deque은 블록 내부에서는 연속적이나 전체적으로는 불연속적인 메모리 구조를 띄고있다.

- push_front()는 어떻게 동작할까?

데이터 블록은 앞에 여유공간이 있으면 그냥 배치를 하고 여유공간이 없으면 새로운 데이터 블록을 앞쪽에 할당하고 Map을 통해 연결하면 된다. push_back()도 같은원리

이것으로 인해 O(1)로 처리가능

- 인덱스 접근도 가능한 이유

deque는 각 블록의 크기와 시작위치를 관리하고 있음 그래서 인덱스가 주어지면 어느 블록의 몇 번째 원소인지 계산할 수 있다. 그래서 인덱스 접근도 O(1)

# 두 스레드가 데이터를 안전하게 사용하는 방법

Game Thread에서 게임 상태를 갱신하고 Render Thread에서 렌더링하는것은 맞음
두 스레드가 같은 배열에 접근한다면 역할을 분리해도 문제가 발생할 수 있음
대표적인 해결 방법이 Double Buffering

Buffer A : Render Thread가 현재 읽는 데이터
Buffer B : Game Thread가 다음 프레임을 위해 갱신하는 데이터

Buffer A에서는 이전 프레임 위치가 있고(Render Thread는 이것을 읽음), Buffer B는 새 위치를 계산(Game Thread)
B에서 계산이 완료되면 A를 읽는 작업이 끝날때까지 기다림, 안전한 시점에 두 버퍼의 역할을 교체함
Buffer A는 다음 프레임 준비(Game Thread), Buffer B는 새 프레임 렌더링(Render Thread)

## 갱신이 완료되면 어떻게 전달할까?

Game Thread가 Buffer B에 모든 캐릭터의 위치를 기록했다면
이제 Render Thread에 Buffer B를 읽을 준비가 되었다는 사실을 알려주고, 두 버퍼의 역할을 교체할 수 있음
교체 시점은 스레드간 안전하게 동기화해야됨

> 핵심 : 더블 버퍼링은 두 스레드가 같은 데이터를 동시에 수정/조회하지 않도록 버퍼의 역할을 분리하고, 안전한 시점에 교체하는 방식

# 컴파일러 최적화

```c++
bool bStop = false;

// 작업 스레드
void Worker()
{
    while (!bStop)
    {
        // 반복적으로 작업 수행
    }
}

// Game Thread
void StopWorker()
{
    bStop = true;
}
```

컴파일러는 일반 변수 bStop의 값이 반복문 내부에서 변경되지 않는다고 판단하면, 매번 메모리에서 읽는 작업을 생략하도록 최적화 할 수 있음
컴파일러가 bStop을 처음 한 번만 읽고 이후에는 같은 값을 사용하도록 최적화할 수 있음
그러면 다른 스레드가 true를 기록하더라도 작업 스레드가 변경을 확인하지 못할 수 있음

컴파일러 최적화는 코드가 정상적으로 동작한다는 가정을 하는데 지금은 최적화때문에 데이터 레이스가 발생할 수 있는 상황이다.

# SIMD와 SoA, AoS

SIMD는 앞서 배운것처럼 여러데이터에 같은 연산을 수행하는 기술

- AoS(Array of Structures) : 구조체들의 배열

한 적에게 필요한 데이터를 하나의 구조체에 모아서 관리하는 방식

```c++
struct Enemy
{
    float X, Y;
    float VX, VY;
};

std::vector<Enemy> Enemies;
```

메모리에는

```
적 1          적 2          적 3
[X Y VX VY] [X Y VX VY] [X Y VX VY]
```

- SoA(Sturcture of Arrays) : 배열들로 구성된 구조체
  각 데이터의 종류별로 배열로 따로 관리하는 방식

```c++
struct Enemies
{
    std::vector<float> X;
    std::vector<float> Y;
    std::vector<float> VX;
    std::vector<float> VY;
};
```

메모리에는

```
X  : [X1  X2  X3]
Y  : [Y1  Y2  Y3]
VX : [VX1 VX2 VX3]
VY : [VY1 VY2 VY3]
```

이렇게 저장됨, 장점 : 모든 적의 X좌표처럼 같은 종류의 데이터를 일괄 처리할 때 유리함

- SoA가 SIMD에 유리한 이유

적 1000명의 X좌표만 갱신한다고 했을때

```c++
X[i] += VX[i] * DeltaTime;
```

AoS라면 X좌표 사이에 Y,VX,VY등이 껴서 필요한 데이터만 연속으로 읽기 어렵지만 SoA라면 X와 VX가 연속된 배열에 있어서 SIMD 레지스터에 효율적으로 가져오기 쉬움

다만 SoA가 항상 빠른건 아니다. 적 한 명의 모든 데이터를 함께 처리한다면 AoS가 더 적합할 수도 있다.
