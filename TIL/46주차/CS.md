# atomic

가장 헷갈리는 부분
atomic은 락을 거는것이 아니고 원자적 연산을 보장해주는것
atomic은 연산을 쪼개지지 않게 보장 + 여러 코어에서 그 atomic값의 변경을 일관되게 관찰하도록 함
atomic을 안써도 캐시 일관성 프로토콜은 동작을 한다. 하지만 두 스레드가 하나의 변수에 대해서 읽고 둘다 값을 쓰는 경쟁상태까지는 막아주지 못한다.

여러 변수 사이의 상태 일관성은 자동으로 묶어주지 않는다.

```c++
struct PlayerState
{
    int HP = 100;
    bool IsDead = false;
};
```

// Thread A

```c++
HP -= 100;

if (HP <= 0)
    IsDead = true;
```

// Thread B

```c++
if (!IsDead)
{
    // 살아있는 플레이어라고 판단하고
    // 어떤 행동을 수행
}
```

여기서 HP, IsDead를 atomic으로 바꾸어도 이 문제는 해결되지 않는다.

ThreadA작업중에

```c++
HP -= 100;        // HP = 0

// 이 사이에 Thread B가 실행될 수 있음

IsDead = true;
```

---

mutex를 써서 해결할 수 있다.

```c++
struct PlayerState
{
    int HP = 100;
    bool IsDead = false;
    std::mutex Mutex;
};
```

// Thread A

```c++
{
    std::lock_guard lock(Mutex);

    HP -= 100;
    if (HP <= 0)
        IsDead = true;
}
```

// Thread B

```c++
{
    std::lock_guard lock(Mutex);

    if (!IsDead)
    {
        // 행동
    }
}
```

# 객체 슬라이싱

```c++
#include <iostream>

class Character
{
public:
    virtual void Attack()
    {
        std::cout << "Character Attack\n";
    }
};

class Player : public Character
{
public:
    void Attack() override
    {
        std::cout << "Player Attack\n";
    }
};

void DoAttack(Character character)
{
    character.Attack();
}

int main()
{
    Player player;
    DoAttack(player);
}
```

Player전체가 함수 안으로 유지되는게 아니고 Character에 해당하는 부분만 복사되어 별도의 Character 객체가 만들어진다. Player부분은 잘려나간다. 이걸 object slicing(객체 슬라이싱)이라고 한다

# forwarding reference

```c++
template<typename T>
void Func(T&& value);
```

보통 이런 형태에서 T가 함수 호출 시 추론되는 경우 T&&를 forwarding reference라고 함

```c++
int x = 10;

Func(x);   // x는 lvalue
           // T = int&
           // T&& = int& && → int&

Func(20);  // 20은 rvalue
           // T = int
           // T&& = int&&
```

C++ 제작자들은 Forward(T&&) 하나로 lvalue와 rvalue를 둘다 받고 싶어했고 lvalue(x)가 들어오면 타입 T자체를 int가 아니라 int&로 추론하자고 약속

# SIMD

하나의 명령으로 여러 데이터를 동시에 계산하는 방식

```
a[0] + b[0]
a[1] + b[1]
a[2] + b[2]
a[3] + b[3]
```

이렇게 4번연산한다면 SIMD는 개념적으로

```
[a0 a1 a2 a3]
+
[b0 b1 b2 b3]
=
[c0 c1 c2 c3]
```

처럼 한 번에 여러 원소를 병렬로 처리한다.

## 한 SIMD명령안에서는 같은 타입만 계산 가능한가?

한 SIMD명령 안에서는 보통 같은 타입/같은 크기의 데이터끼리 계산한다고 본다.

```
float 4개 + float 4개
int 4개   + int 4개
```

이런식이라서 128비트 SIMD 레지스터라면

```
float 32비트 × 4개
int32 32비트 × 4개
int16 16비트 × 8개
int8  8비트  × 16개
```

처럼들어갈 수 있다.
결론적으로 핵심은

> 같은 연산을 여러 데이터에 동시에 적용한다.
> Single Instruction Multiple Data

```c++
Position[i] += Velocity[i] * DeltaTime;
```

캐릭터 위치 업데이트를 캐릭터 1000개에 반복한다면 SIMD가 잘먹히는 대표적인 경우이다.

# Net Relevancy

이 Actor 정볼를 이 클라이언트에게 지금 보내줄 필요가 있느냐?
100명의 플레이어가 있는 큰 맵에서 내 위치에서 수 km 떨어진 플레이어까지 매 프레임 복제할 필요는 없다.

중요한건 Relevancy는 클라이언트마다 따로 판단한다. 같은 Actor라도 A 플레이어에게는 Relevant이고, B 플레이어에게는 Not Relevant일 수 있다. 언리얼은 기본적으로 AActor::IsNetRelevantFor()를 통해 특정 Connection에 대해 이 Actor가 Relevant한지를 판단한다.

보통

- 거리
- 소유한 클라만
- 자기 Owner의 판단 따라가기
- 일정 거리안에서
- 거리에 상관없이

등등의 조건이 있다.

```
Actor가 Replication 대상인가?
        ↓
    bReplicates
        ↓
이 Connection에게 보낼 필요가 있는가?
        ↓
    Net Relevancy
        ↓
      Relevant
        ↓
실제로 복제 후보가 됨
```

bReplicated = true라고 해도 Not Relevant면 복제를 하고 있지 않는다.

# vector

## emplace_back과 push_back의 차이

emplace_back은 전달받은 인자로 컨테이너 내부에서 객체를 직접 생성한다.
push_back은 이미 만들어진 객체를 컨테이너에 복사/이동해서 넣음

```c++
class Player
{
public:
    Player(int hp, int level);
};

std::vector<Player> players;
```

- push_back

```c++
Player p(100, 5);
players.push_back(p);
```

```
1. Player p 생성
2. vector 내부에서 Player 저장 공간 준비
3. p는 lvalue
4. p를 이용해 vector내부 Player를 복사 생성
```

- emplace_back

```c++
players.emplace_back(100, 5);
```

여기서는 바깥 p를 먼저 만들지 않음

```
1. vector 내부 메모리 확보
2. 그 위치에서 바로 Player()호출
3. Player생성
```

# 인접 리스트

게임 월드에 지역이 10,000개 있다고 하자.
각 지역은 평균적으로 3~4개의 다른 지역과만 연결되어 있다.

예를 들면

```
A → B, C
B → A, D
C → A, E, F
...
```

게임에서는 다음 작업을 자주 한다.

- 특정 지역에서 바로 이동 가능한 지역들을 모두 조회
- 새로운 지역 연결을 가끔 추가
- 두 지역 사이에 직접 연결이 있는지 확인
  이 연결 정보를 저장하는 방식을 설계해야 한다.
  다음 기준으로 설명해봐.

1. 어떤 형태로 데이터를 저장하겠는가?
2. 지역이 10,000개지만 실제 연결 수는 적다는 점이 왜 중요한가?
3. 모든 지역끼리의 연결 여부를 2차원 형태로 저장하는 방식과 비교하면 메모리 사용은 어떻게 달라지는가?
4. 특정 지역의 이웃들을 전부 순회할 때 어느 방식이 더 유리한가?

---

희소 그래프를 어떻게 저장할 것이냐

```
인접 리스트
-> 실제 연결된 3~4개만 순회
-> O(degree)

인접 행렬
-> 10000칸을 전부 확인
-> O(V)
```

두 지역이 직접 연결됐는지만 확인하면 인접 행렬은 O(1)이라 더 빠르고, 단순 vector기반 인접 리스트는 이웃 수 만큼 찾아야 해서 O(degree)다.

희소 그래프 이므로 인접 리스트를 사용한다.

# 위상 정렬

게임 빌드 시스템에 다음 작업들이 있다고 하자.

```
A: 캐릭터 데이터 생성
B: 무기 데이터 생성
C: 전투 데이터 생성
D: 최종 게임 데이터 패키징
```

그런데 실행 순서에 제약이 있다.

```
A가 끝나야 C 실행 가능
B가 끝나야 C 실행 가능
C가 끝나야 D 실행 가능
```

작업이 수천 개까지 늘어날 수 있고, 각 작업마다 여러 선행 작업이 존재할 수 있다.
목표는 모든 선행 조건을 만족하면서 실행 가능한 순서를 만들어내는 것이다.
다음을 설명해봐.

1. 작업과 선행 관계를 어떤 형태로 표현하겠는가?
2. 현재 바로 실행할 수 있는 작업은 어떻게 판단할 수 있을까?
3. 작업 하나가 완료되면 나머지 작업들의 상태를 어떻게 갱신하겠는가?
4. 작업들 사이에 A → B → C → A처럼 서로 물려 있다면 어떤 문제가 생기는가?

---

방향이 있는 그래프에서 선행 조건을 만족하는 실행 순서를 찾는 문제
보통 진입차수를 쓴다 indegree, indegree가 0이되면 진입차수가 없기때문에 바로 실행 가능
대표 구현은 Kahn 알고리즘

```
1. 각 노드들의 indegree 계산
2. indegree == 0 인 노드를 큐에 삽입
3. 하나 꺼내서 처리
4. 연결된 다음 노드들의 indegree를 1감소
5. 0이 되면 큐에 삽입
6. 반복
```

사이클이 있으면 아무도 indegree가 0이되지 못하는 구간이 생긴다. 즉, 사이클이 있다 -> 위상 정렬 불가하다

# BST

게임 서버에서 플레이어들의 점수가 계속 바뀐다고 하자.
조건은 다음과 같다.

- 플레이어 수는 100,000명
- 매초 많은 플레이어의 점수가 변경됨
- 현재 점수가 가장 높은 플레이어 10명을 자주 조회
- 전체 순위 전체를 매번 출력할 필요는 없음
- 점수 변경 때마다 전체 100,000명을 다시 정렬하면 너무 비쌈
  이 상황에서 어떤 방식으로 관리하겠어?
  다음을 설명해봐.

1. 전체 정렬을 매번 다시 하는 방식이 왜 비효율적인지
2. 상위 10명만 필요하다는 조건을 어떻게 활용할 수 있을지
3. 점수가 변경될 때 어떤 식으로 자료를 갱신할지
4. 조회 비용과 갱신 비용 사이에서 어떤 트레이드오프가 생길지

---

균형 BST, C++의 예시로는 set이나 multiset

1. 전체 정렬을 매번 하면 플레이어 100000명에 대해 매번 O(N log N)이 든다. 점수 변경이 초당 많이 발생하면 너무 비쌈
2. 상위 10명만 필요하므로 전체 순위를 다시 계산할 필요가 없다. 점수 순서가 유지돼 있다면 높은 점수 쪽에서 10명만 순회하면 된다.
3. 점수가 바뀌면 기존(점수, 플레이어ID)를 제거하고 새 점수로 다시 삽입

```
기존 점수 제거 -> O(log N)
새 점수 삽입 -> O(log N)
상위 10명 조회 -> O(10)
```

4. 트레이드 오프는

```
정렬 상태를 계속 유지
-> 점수 갱신은 O(log N)
-> 상위 10명 조회는 매우 빠름

정렬 상태를 유지하지 않음
-> 점수 갱신은 거의 O(1)
-> 조회할 때마다 전체를 훑어야 함
```

# 세그먼트 트리

배열 구간의 정보를 트리 형태로 미리 저장해서 구간 조회와 값 변경을 둘다 O(log N)에 처리하는 자료구조

```
배열값이 자주 바뀜
+
구간 합 / 구간 최솟값 / 구간 최대값을 자주 구함
```

---

배열 전체를 구간별로 계속 반씩 나눠서 합을 저장

```
[2, 1, 5, 3, 4, 7, 6, 8]

루트는 전체합
[0 ~ 7] = 36
```

이를 절반으로 나눔

```
                  [0~7] = 36
                /             \
         [0~3] = 11         [4~7] = 25
->
                    [0~7] 36
                 /             \
           [0~3] 11           [4~7] 25
           /     \             /     \
       [0~1]3  [2~3]8     [4~5]11  [6~7]14
->
                        [0~7] 36
                   /                \
              [0~3]11              [4~7]25
             /      \              /      \
          [0~1]3   [2~3]8      [4~5]11   [6~7]14
          /   \     /   \       /   \      /   \
         2     1   5     3     4     7    6     8
```

[2~5] 누적합을 찾는다고 하면
[2~3] + [4~5] 이런식으로 찾는다.
만약에 값 변경이 들어간다면 index2를 변경한다고 하면 index2가 포함된 구간만 수정하면 된다.
트리여서 조회, 변경이 O(log N)이다.
