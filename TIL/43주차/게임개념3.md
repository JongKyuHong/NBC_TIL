# std::condition_variable - 조건 변수

게임에서 Worker Thread(작업 스레드)가 있다고 하자
Worker는 처리할 Job(작업)이 없으면 할 일이 없다.

가장 단순히 예를 들면

```c++
while (true)
{
    if (!Jobs.empty())
    {
        ExecuteJob();
    }
}
```

이렇게 계속 Queue를 확인할 수 있다.
문제는 Job이 없어도 CPU를 계속 사용한다는 점

```
Job 없음
↓
확인
↓
없음
↓
확인
↓
없음
↓
확인...
```

이걸 Busy Waiting(바쁜 대기)라고 한다.
우리가 원하는건

```
Job 없음
↓
Worker를 재움
↓
새 Job 들어옴
↓
Worker 깨움
↓
Job 실행
```

## 핵심 구조

```c++
std::queue<Job> Jobs;
std::mutex Mutex;
std::condition_variable CV;
```

보통 세가지가 나온다.

```
Jobs
= 실제 상태

Mutex
= Jobs를 여러 Thread가 동시에 건드리지 못하게 보호

Condition Variable
= "상태가 바뀌었으니 다시 확인해봐"라고
  잠자는 Thread를 깨움
```

여기서 중요한것은

> Condition Variable 자체가 조건을 저장하는게 아니다.

실제 조건은

```c++
!Jobs.empty()
```

### Worker

```c++
void Worker()
{
    while (true)
    {
        std::unique_lock<std::mutex> Lock(Mutex);
        CV.wait(Lock, [] {
            return !Jobs.empty();
        })
    }
}

```

### unique_lock을 왜 쓰는가?

Mutex를 잠글 때

```c++
std::lock_guard<std::mutex> Lock(Mutex);
```

이런식으로 사용한다.
그런데 `condition_variable::wait()`에는 보통

```c++
std::unique_lock<std::mutex>
```

을 사용한다.

왜냐하면 wait()가 실행되는 동안 Mutex를

```
잠금
↓
풀기
↓
다시 잠그기
```

해야 하기 때문에

`lock_guard`는

> 생성할때 Lock -> Scope 종료 때 Unlock

이라는 단순한 RAII도구라서 중간에 자유롭게 풀었다가 다시 잡는 용도가 아니다.
반면 `unique_lock`은

```c++
Lock.unlock();
Lock.lock();
```

처럼 Lock 상태를 직접 변경할 수 있다.
그래서 `condition_variable`과 함께 사용한다.

### Wait()에서는 실제로 무슨일이 벌어지는가?

현재 Worker가

```c++
std::unique_lock<std::mutex> Lock(Mutex);
```

를 실행했다.
현재 상태는 Worker가 Mutex를 소유한상태
그리고

```c++
CV.wait(Lock);
```

을 호출한다.
개념적으로 다음 일이 일어난다.

```
1. Worker가 Mutex를 가지고 있음
2. wait()호출
3. Mutex를 해제하면서 동시에 Condition Variable 대기 상태로 들어감
4. Worker Thread Sleep
5. 다른 Thread가 Notify
6. Worker가 깨어남
7. Mutex를 다시 획득
8. wait() 반환
```

중요한 부분은 3번

> Mutex해제와 대기 진입이 원자적으로 연결되어 있다.

### 왜 원자적으로 해제하고 대기해야 하나

이게 안 되면 이런 문제가 가능하다.

Worker

```
Queue 확인
-> 비어 있음
-> Mutex unlock
```

그 직후 Producer가

```
Job추가
-> notify
```

그런데 Worker는 아직 Sleep 상태에 들어가기 전이었다고 하자

```
notify 발생
↓
깨울 사람이 없음
↓
notify 사라짐
↓
Worker 이제 Sleep
```

Worker는 Job이 있는데도 계속 잘 수 있다.
이런 종류의 문제가 Lost Wakeup(깨움 신호 유실)과 연결된다.

`conditon_variable::wait()`는
Mutex를 푼 다음에 나중에 따로 잠그는 방식이 아니고

> Mutex를 해제하면서 Condition Variable의 대기자로 들어가는 과정을 안전하게 연결한다.

그래서 그 사이의 Race를 막는다.

### Condition Variable은 신호를 저장하지 않는다

Condition Variable은 이벤트 카운터가 아니다.

예를들어

```
Producer
notify_one()

↓ 1초 뒤

Worker
wait()
```

이면 과거의 notify_one()을 기억했다가 Worker를 바로 깨워주는게 아니다.
그래서 condition Variable을 사용할때는 항상

> Notification(알림)을 믿는게 아니라 실제 상태를 확인해야 한다

여기서 조건식 - Predicate가 나온다

### Predicate가 왜 필요한가?

```c++
CV.wait(Lock, [] {
    return !Jobs.empty();
});
```

이건 개념적으로

```c++
while (Jobs.empty()){
    cv.wait(Lock);
}
```

과 비슷하다.

즉, Worker가 깨어났다고 해서 바로

```c++
Jobs.front();
```

를 실행하지 않는다.
반드시 `진짜 Job이 생겼는가?`를 다시 확인한다.

### Spurious Wakeup(허위 깨움)

Thread가 notify_one이나 notify_all을 명시적으로 받지 않았는데도 wait()에서 깨어나는 경우가 있을 수 있다.
이걸 Spurious Wakeup(허위 깨움 / 가짜 깨움) 이라고 한다.

그래서 `CV.wait(Lock);` 만 하고나서 `Jobs.front()`를 바로하면 위험하다

대신

```c++
while (Jobs.empty())
{
    CV.wait(Lock);
}

// 위처럼 쓰거나

CV.wait(Lock, [] {
    return !Jobs.empty();
});

// 아래처럼 써서 반드시 실제 조건을 다시 검사해야한다.
```

### Predicate는 Lost Wakeup에도 도움을 준다.

예를들어 Worker가 `wait()`에 들어가기 전에 이미 Producer가 Job을 넣었다고 하자

```
Jobs.push(Job);
notify_one();

↓

Worker 시작
```

Notification은 이미 지나갔지만 Worker가

```c++
CV.wait(Lock, []{
    return !Jobs.empty();
});
```

를 호출하면 먼저 Predicate를 검사한다

```c++
Jobs.empty() == false;
```

조건이 이미 만족했기 때문에 Worker는 아예 잠들지 않는다.

```
과거 notify 기억 → X

실제 Queue 상태 확인 → O
```

그래서 Condition Variable에서는 알림보다 상태가 중요하다.

### 용어

```
Producer는 작업을 만들어서 Queue에 넣는쪽
Worker Thread는 큐에서 작업을 꺼내서 처리하니까 Consumer라고 부름

작업 하나 생김
→ notify_one

전체 상태 변경 / 종료
→ notify_all
```

## 정리

```
Worker
↓
Mutex Lock
↓
Predicate 검사

조건 false
↓
wait()
↓
Mutex를 원자적으로 Unlock + Sleep

notify
↓
Wake

Mutex 다시 Lock
↓
Predicate 다시 검사

조건 true
↓
작업 가져옴
↓
Mutex Unlock
↓
실제 작업 수행
```
