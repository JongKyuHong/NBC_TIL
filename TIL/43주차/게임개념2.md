# Index + Generation Handle

## 상황

몬스터를 이런 배열로 관리한다고 치자

```c++
std::vector<Enemy> Enemies;
std::vector<uint32_t> FreeList;
```

슬롯 상태가 처음에는

```
Index
0 : Enemy A
1 : Enemy B
2 : Enemy C
3 : Enemy D
```

다른 시스템이 Enemy B를 기억해야 해서 단순히 인덱스를 저장했다.

```
uint32_t TargetIndex = 1;
```

이후 Enemy B가 죽었다면

```
0 : Enemy A
1 : Empty
2 : Enemy C
3 : Enemy D

FreeList = [1]
```

그리고 새로운 Enemy E가 생성된다.
Free List에서 1을 꺼내 재사용하면

```
0 : Enemy A
1 : Enemy E
2 : Enemy C
3 : Enemy D
```

그런데 예전 시스템은 여전히

```
TragetIndex = 1
```

을 가지고 있다.

이제 이 인덱스로 접근하면 원래 기억했던 Enemy B가 아니라 전혀 상관없는 Enemy E를 가져온다.

FreeList는

> 빈 슬롯을 빠르게 찾아서 재사용하는 방법

유효한 다른 객체를 잘못 가리키는것을 방지하기 위해서는

Index와 Generation을 같이 저장한다.

Generation은

> 해당 슬롯이 몇 번째 객체를 담고 있는지를 나타내는 버전 번호

**처음 상태**

```
Index 0 : Enemy A   Generation 0
Index 1 : Enemy B   Generation 0
Index 2 : Enemy C   Generation 0


Enemy B는
Index      = 1
Generation = 0

Handle { 1, 0 }
```

**Enemy B를 삭제**

Index 1을 비움 -> 그리고 Generation을 증가시킴

```
Index 1 : Empty
Generation : 1
```

이렇게 하고 FreeList에 1을 넣음

**Enemy E 생성**

```
Index 1 : Enemy E
Generation = 1

Handle { 1, 1 }
```

예전 B의 Handle은 {1, 0}이므로 검사하면 불일치 따라서 이 Handle은 더 이상 유효하지 않음을 알 수 있다.

## 핵심 구조

슬롯에는 객체뿐 아니라 Generation도 같이 둔다.

```c++
struct EnemySlot
{
    Enemy EnemyData;
    uint32_t Generation = 0;
    bool bOccupied = false;
};
```

Handle은

```c++
struct EnemyHandle
{
    uint32_t Index;
    uint32_t Generation;
};
```

형태

## 예제

```c++
struct EnemyHandle
{
    uint32_t Index;
    uint32_t Generation;
};

struct EnemySlot
{
    Enemy Data;
    uint32_t Generation = 0;
    bool bOccupied = false;
};
```

```c++
class EnemyManager
{
private:
    std::vector<EnemySlot> Slots;
    std::vector<uint32_t> FreeList;

public:
    EnemyHandle CreateEnemy()
    {
        uint32_t Index;

        if (!FreeList.empty())
        {
            Index = FreeList.back();
            FreeList.pop_back();
        }
        else
        {
            Index = static_cast<uint32_t>(Slots.size());
            Slots.emplace_back();
        }

        EnemySlot& Slot = Slots[Index];
        Slot.bOccupied = true;

        return EnemyHandle{
            Index,
            Slot.Generation
        };
    }

    void DestroyEnemy(EnemyHandle Handle)
    {
        if (!IsValid(Handle))
            return;

        EnemySlot& Slot = Slots[Handle.Index];

        Slot.bOccupied = false;

        // 이 슬롯에서 기존 Handle을 모두 무효화
        ++Slot.Generation;

        FreeList.push_back(Handle.Index);
    }

    bool IsValid(EnemyHandle Handle) const
    {
        if (Handle.Index >= Slots.size())
            return false;

        const EnemySlot& Slot = Slots[Handle.Index];

        return Slot.bOccupied &&
               Slot.Generation == Handle.Generation;
    }

    Enemy* GetEnemy(EnemyHandle Handle)
    {
        if (!IsValid(Handle))
            return nullptr;

        return &Slots[Handle.Index].Data;
    }
};
```

사용자는 직접

```c++
Enemies[Handle.Index]
```

로 접근하지 않고

```c++
Enemy* EnemyPtr = Manager.GetEnemy(Handle);
```

처럼 검증을 거친다.

## 왜 포인터보다 유용할 수 있는가?

예를들어 다른 시스템이

```c++
Enemy* Target;
```

을 보관한다고 할때 Enemy가 삭제되면 이 Pointer는 Dangling Pointer가 될 수 있다.
반면 Handle은

```c++
EnemyHandle Target;
```

을 저장한다.

```c++
if (Enemy* Enemy = Manager.GetEnemy(Target))
{
    Attack(*Enemy);
}
```

사용시 이런식으로 검사한다.

```
객체 삭제
↓
Generation 증가
↓
예전 Handle 자동 무효화
```

# Data Race와 Race Condition, Critical Section

## Data Race

C++기준에서는

같은 메모리 위치에

1. 여러 Thread가 동시에 접근하고
2. 그중 하나 이상이 Write(쓰기)를 하고
3. 적절한 Synchronization(동기화)이 없다.

```c++
int HP = 100;

// Thread A
HP -= 10;

// Thread B
HP += 20;
```

동기화가 없다면 Data Race이다.

> C++의 Data Race는 Undefined Behavior(정의되지 않은 동작)이다.
> 즉, 단순히 둘중 하나의 결과가 나오는게 아니고 컴파일러 입장에서 프로그램 동작 자체가 보장되지 않는다.

## Race Condition

더 넓은 개념이다.

> Thread 실행 순서나 타이밍에 따라서 프로그램의 논리적 결과가 달라지는 상태

Data Race가 없어도 Race Condition은 생길 수 있다.

```c++
아이템 재고 = 1

// Thread A, B
if (Stock > 0)
{
    Buy();
}
```

Thread A, B가 똑같이 실행한다.
각각의 Stock 접근 자체는 Mutex로 안전하게 만들었다고 해보자

```
Thread A
재고 확인 → 1

Thread B
재고 확인 → 1

Thread A
구매

Thread B
구매
```

그래도 위가 가능하다면 아이템 하나를 두명이 구매할 수 있다.
즉, 개별 메모리 접근에는 Data Race가 없더라도, 확인 -> 꾸매 라는 논리 전체가 원자적으로 처리되지 않아서 Race Condition이 생긴 것

```
Data Race
= 메모리 접근 자체의 동기화 문제

Race Condition
= 실행 순서 때문에 논리가 깨지는 더 넓은 문제
```

## Critical Section(임계구역)

여러 Thread가 동시에 실행하면 안 되는 코드 구간을 묶어야 한다.
그 구간이 Critical Section(임계 구역)이다.

```c++
if (Stock > 0)
{
    --Stock;
    GiveItem();
}
```

전체가 하나의 논리 단위
이 부분 전체를 보호해야 한다.

```c++
std::mutex Mutex;

void Buy()
{
    std::lock_guard<std::mutex> Lock(Mutex);

    if (Stock > 0)
    {
        --Stock;
        GiveItem();
    }
}
```

여기서

```c++
std::lock_guard<std::mutex> Lock(Mutex);
```

부터 scope가 끝날 때까지가 실질적인 Critical Section이 된다.

Atomic은 개별 연산의 원자성을 보장

```
현재 접속 플레이어 수
현재 살아있는 몬스터 수
작업 완료 Flag
```

Mutex는 한번에 하나의 Thread만 Critical Section에 들어오게 하는 도구

```
Player Inventory
├ Gold
├ Item List
└ Equipment

처럼 여러 값이 함께 일관성을 유지해야 하는 경우
```

Semaphore는 동시에 특정 자원을 사용할 수 있는 Thread 수를 제한한다.

```
Texture Streaming Worker는 최대 4개
Network Compression Job은 최대 8개
DB Connection은 최대 16개

동시에 몇개까지 들어올 수 있는가
```

# DeadLock 예방 방법

## 발생 조건

너무 유명하긴 하지만 항상 기억 안나는 부분

- 상호 배제 : 자원을 한번에 하나의 Thread만 사용
- 점유 대기 : 하나를 가진 채 다른 자원을 기다림
- 비선점 : 다른 Thread의 Lock을 강제로 뺏을 수 없음
- 순환 대기 : A는 B를 기다리고 B는 A를 기다림

여기서 순환대기 (Circular Wait)을 어떻게 꺠는지가 중요

## Lock Ordering(락 순서 규칙)

가장 대표적인 예방방법

> 여러 Lock을 획득해야 할 때 항상 같은 순서로 획득

예를들어 규칙을

```
InventoryMutex
↓
PlayerStateMutex
↓
QuestMutex
```

로 정한다
모든 코드가

```
lock(InventoryMutex);
lock(PlayerStateMutex);
```

이 순서만 사용한다 반대의 경우가 없기때문에 순환대기는 발생하지 않는다.

```c++
void Trade()
{
    std::lock_guard<std::mutex> LockA(InventoryMutex);
    std::lock_guard<std::mutex> LockB(PlayerStateMutex);
}

void SavePlayer()
{
    std::lock_guard<std::mutex> LockA(InventoryMutex);
    std::lock_guard<std::mutex> LockB(PlayerStateMutex);
}
```

둘다 같은 순서를 따름

## std::scoped_lock

C++에서는 여러 Mutex를 동시에 안전하게 잠그고 싶을때

```c++
std::scoped_lock Lock(InventoryMutex, PlayerStateMutex);
```

내부적으로 Deadlock을 피하도록 여러 Mutex를 획득한다.

## DeadLock 예방에서 더 중요한것

게임 코드에서는 Lock을 오래 잡지 않는 것도 중요하다.

```c++
lock(Mutex);

// 네트워크 요청
// 파일 IO
// 긴 AI 계산

unlock(Mutex);
```

이런 코드는 위험하다
Lock Contention(락 경합)이 심해지고 다른 Thread들이 오래 기다림
그래서 Critical Section(임계 구역)은 가능한 짧게 유지하는게 좋다.

## Starvation

Starvation(기아상태)는 특정 Thread가 계속 Lock을 얻지 못해서 사실상 진행 못한는 경우고
데드락은 서로 기다려서 아무도 진행 못하는것

# Frustum / Occlusion Culling

## Frustum Culling

카메라의 시야를 3D공간으로 보면 보통 이런 형태다

```
        Far Plane
       /---------\
      /           \
     /             \
    /               \
   /                 \
  /-------------------\
      Near Plane
         Camera
```

이 공간을 View Frustum(뷰 프러스텀 / 시야 절두체)라고 한다.
보통 6개의 Plane(평면)으로 경계를 만든다

```
Left
Right
Top
Bottom
Near
Far
```

즉, 오브젝트가 이 6개 평면 안에 있는지를 검사한다.

### 왜 Mesh 전체를 검사하지 않나

오브젝트가 복잡한 Mesh일때 Frustum검사할때 Triangle하나하나 검사하면 너무 비쌈
그래서 보통 간단한 Bounding Volume(바운딩 볼륨 / 경계 볼륨)을 쓴다.

대표적으로

- Bounding Sphere(경계 구) -> 계산이 단순, 회전해도 형태가 그대로라 관리 쉬움, 길쭉한 오브젝트 감싸면 빈 공간이 많아짐
- AABB(Axis-Aligned Bounding Box, 축 정렬 경계 상자) -> 일반 오브젝트 형태를 Sphere보다 촘촘하게 감쌈, 검사 계산이 복잡

## Occlusion Culling(가림 컬링)

> 다른 오브젝트 때문에 실제 화면에 안 보이는 오브젝트를 제외하는 것

GPU의 깊이 정보를 이용함
Depth Buffer에는 이 픽셀에서 가장 가까운 표면 깊이가 들어있다.

## 수천개 Object를 전부 Frustum 검사하면?

부담이 많이 되기 때문에 공간을 묶는다.

```
World
├─ Region A
│   ├─ Object 1
│   ├─ Object 2
│   └─ Object 3
│
├─ Region B
│   ├─ Object 4
│   └─ Object 5
```

먼저 Region A의 Bounding Box를 검사한다.
Region A 전체가 Frustum밖이면 Object 1,2,3는 전부 버림
이게 계층 구조 (Spatial Hierarchy)를 사용하는 이유

2D나 평면 중심 공간이라면 Quadtree(쿼드트리 / 사분 트리)
3D 공간이라면 Octree(옥트리 / 팔분 트리)

```
World
↓
8개 공간으로 분할
↓
각 공간 다시 8개로 분할
↓
...
```

Frustum 검사

```
Root 검사
↓
밖이면 전체 제거

안이면 Child 검사
↓
밖인 Child 제거

안에 있는 Child만 더 내려감
```
